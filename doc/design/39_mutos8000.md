## A2. Starten

1. Ladediskette in A:, **sonst kein Laufwerk bestückt** (eine MUTOS-Diskette in B:–D: beim Start → UDOS meldet `DISK INITIALIZATION ERROR C6` bzw. `I/O ERROR C2 ON UNIT 00`, der Lader erscheint nicht; §2.  Ursache: `ZDOS` meldet beim Start alle Einheiten an, §11.6).
   **Ausnahme:** die Ladedisketten `…_nur_a` und `…_8x512` — dort dürfen Wurzel (C:) und Datendisketten von Anfang an liegen, Schritt 3 ist dann nur `r`.
2. UDOS zeigt das Lader-Menü `LOADER  M U T O S 8000  V 1.0` (`FORM.B COPY.B FORM.M COPY.M BOOT MUTOS BOOT MUTOS.PIO`).  Eingabe `BOOT MUTOS`.
3. `mutos_io` meldet `remove mutos8000 boot - disk` / `insert mutos8000 root - disk on rk2` / `change / ready (r)..:`.  **Erst jetzt** die Ladediskette
   aus A: nehmen und die Wurzel in **C:** einlegen, `r` (Rückfrage `R`).
4. `mem = 196608`, `single user login:` → `root` (kein Kennwort), `MUTOS 8000 V.1.0`, Datum, Prompt `#`.  Laufzeit im Emulator ≈ 8–10 s Rechenzeit.

Im Debugger (Vorlage für eigene Abläufe, = Wächter `cli_mutos8000_boot_ladediskette_k5601`):

```
tools/dev.sh tool k1520dbg --em em256 --laufwerke K5601,K5601,K5601 disks/a5120_16_MUTOS/a5120_mutos8000_boot_udos_k5601.hfe
g 80000000
keys BOOT\sMUTOS\r
g 100000000
eject A
mount C disks/a5120_16_MUTOS/a5120_mutos8000_root_mfm.hfe udos_ss77
keys r
g 100000000
keys root\r
g 100000000
screen
```

`k1520dbg` mountet als Kopie (COW); mit `--rw` bleiben Schreibzugriffe erhalten (dann nur an eigenen Kopien arbeiten).  In der Oberfläche `a5120emu`
(Modell A5120 mit EM256) dasselbe über den Laufwerkskasten: Ladediskette einlegen, starten, nach der Aufforderung tauschen (in der Oberfläche nicht eigens erprobt; alle Messungen mit `k1520dbg`).

## A4. Einhängen und aushängen

* **Laufwerk = Gerät:** A: = `/dev/rk0`, B: = `rk1`, C: = `rk2` (Wurzel), D: = `rk3` (Major 4, Minor 0–3; `rrk0–3` die zeichenorientierten Gegenstücke).
  Nach dem Start ist **A: frei** (die Ladediskette wird nicht mehr gebraucht), dazu B: und — mit `FFH`/`FEH` — D:.
* **Einhängen** (als `root`): Diskette einlegen, `/etc/mount /dev/rk0 /mnt`.  Zur Laufzeit, kein Neustart.  Beispiel drei K5601: usr in A:, cmd in B:,
  `/etc/mount /dev/rk0 /usr`, `/etc/mount /dev/rk1 /mnt`.
* **Aushängen:** `/etc/umount /dev/rk0`, **erst dann** die Diskette herausnehmen.  Eingehängt ist schreibbar; der Kernel schreibt verzögert zurück
  (`sync` vor dem Ausschalten).  Befehle, die auf der ausgehängten Diskette lagen (z. B. `/mnt/bin/…`), sind danach weg.
* **Aufzeichnung muss zum Laufwerk passen:** MF3200 nur FM (Disketten ohne `_mfm`), K5601 nur MFM (`_mfm`).
* **Im Emulator** wird erst NACH der Anmeldung eingelegt: `mount A <abbild> udos_ss77` im Debugger (Format immer `udos_ss77`, auch für FM; die
  DiskTool-Profilnamen `mutos8k_26x128_fm`/`_mfm` sind kein Mount-Format — der Mount wird abgelehnt und MUTOS meldet `err on dev 4/N er=0,302`).
* **Grenzen:** `mount` führt `/etc/mtab` nicht fort (`df` zeigt trotzdem die eingehängten Geräte); es gibt kein `/etc/rc`, das beim Start einhängt;
  ein `mount` auf ein leeres Laufwerk kostet vier Leseversuche und `mount: I/O error`.
* Typische Meldungen: `err on dev 4/N bn=… er=0,302` = Laufwerk N hat in `[0FCAH]` Typ 0 oder ist leer (A9); `er=0,304` = Sektor nicht gefunden
  (falsche Geometrie, z. B. 8 × 512).

## A5. Formatieren und Dateisystem anlegen — unter UDOS und unter MUTOS

Zwei getrennte Schritte: **Formatieren** (Spuren und Sektoren schreiben) und **Dateisystem anlegen** (Superblock, Inodes, Freiliste).

| Schritt | unter UDOS (Lader-Menü) | unter MUTOS | offline |
|---|---|---|---|
| Formatieren 26 × 128 (MUTOS-Datendiskette) | **`FORM.M`**: `drive ?` Ziffer + Enter (A: = `0`, B: = `1` …; Buchstaben treffen das nächste Laufwerk, §9.12), `sectorlength` `0` (= 128) + Enter, `ready ?` `Y` + Enter | **nicht möglich** — kein Formatierprogramm in MUTOS (cmd hat keins, der Kernel bietet keinen Formatierbefehl) | DiskTool: `k1520disktool create neu.hfe --fs udos_ss77` (MFM) bzw. `--fs mutos8k_26x128_fm` (FM) |
| Formatieren UDOS-Format / Ladediskette kopieren | `FORM.B` (übernimmt die Systemspuren von A:), danach `COPY.B V 0 TO 1` (§9.4, §9.13 Verfahren A) | — | `bau_ladediskette.py` (A6) |
| Dateisystem anlegen | — | **`/mnt/etc/mkfs /dev/rkN 494`** (cmd in `/mnt` eingehängt) — Ausgabe `isize = 152`, `m/n = 3 500` | `k1520disktool create neu.hfe --fs mutos8k_26x128_mfm --blocks 494 [--inodes N]` |
| Einhängen / aushängen | — | `/etc/mount`, `/etc/umount` (A4) | — |

**Gemessen (2026-10-24, Emulator, vier K5601, `--rw` an Kopien):**
* **Ganz im Gast:** Lader-Menü → `FORM.M` auf B: (128 B) → Neustart → MUTOS → `mkfs /dev/rk1 494` → `mount /dev/rk1 /usr` → `echo hallo >/usr/x`, `mkdir /usr/d`,
  `ls -l /usr`, `df` (`/dev/rk1 470` freie Blöcke) → `umount` → `mount` → `cat /usr/x` = `hallo`.  Das DiskTool liest die Diskette danach als `mutos8k_26x128_mfm`, `check --full` ohne Befund.
* **Neustart nach `FORM.M` nötig:** direkt nach `FORM.M` scheiterte `BOOT MUTOS` mit `I/O ERROR C2 ON UNIT 00` (Ursache nicht untersucht).  Die frisch formatierte Diskette
  vor dem Neustart herausnehmen (sonst `C6`, A2) und erst nach der Anmeldung wieder einlegen.
* **`mkfs` auf einer DiskTool-formatierten Diskette** (`create --fs udos_ss77`) läuft ebenso.  Wächter `cli_mutos8000_mkfs_k5601` (mkfs auf eine COW-Kopie der bin-Diskette,
  einhängen, schreiben, aus- und wieder einhängen, lesen; ≈ 30 s).
* `mkfs` ohne Angaben legt 152 Inodes an (`isize`) und eine Freiliste mit Schritt 3 (`m/n = 3 500`, wie die Original-Datendisketten).  Für eine **Wurzel** nie 494 nehmen —
  höchstens 250 (Swap, A7).

## A6. Ladediskette bauen

**Mit der Pipeline** (Quelle: Archiv `disks/a5120_mutos8000/a5120_mutos8000_boot_udos.zip` = Dateien der Original-Ladediskette mit UDOS-Beiblatt,
`systemspuren.bin` (Spur 0–2), `bauangaben.yaml`):

```sh
python3 -I tools/mutos8000/bau_ladediskette.py disks/a5120_mutos8000/a5120_mutos8000_boot_udos.zip neu.hfe --laufwerke k5601
#   --laufwerke: mf3200 | k5601 | mf3200_k5601 | k5601_nur_a | mf3200_k5601_nur_a | k5601_8x512
python3 -I tools/mutos8000/bau_alle.py --ueberschreiben            # alle zwanzig Disketten nach disks/a5120_16_MUTOS/
```

Ablauf im Skript: `create` im Profil (`udos_ss77` MFM bzw. `udos_ss77_fm` FM), `boot-put` der Systemspuren **mit gepatchter Laufwerkstyp-Konstante** (A9), Dateipatches der Variante
(unten), `put` der Dateien, `check --full`, Gegenprobe (Konstante zurückgelesen; gepatchte Dateien gleich dem erwarteten Patchergebnis, alle übrigen byteweise gleich dem Archiv).  Zwei Bauten sind bitgleich.

**Dateipatches je Variante** (Bauangaben `patch_<variante>_<n>: <Datei> <Art> [opt=zahl …]`, angewandt beim Bau auf eine Kopie der Archivdateien mit den Funktionen von
`tools/mutos8000/mutos_patch.py` — jedes Altbyte wird geprüft, im Archiv liegen nur die Originale):

| Variante | Patches | Zweck |
|---|---|---|
| `k5601_nur_a`, `mf3200_k5601_nur_a` | `ZDOS zdos-einheit0` | UDOS meldet beim Start nur A: an (§11.6) |
| `k5601_8x512` | `mutos_io io-8x512`, `ZDOS zdos-einheit0`, `mutos_1216 kern swplo=352 nswap=256` | DISK-Satz (§11.2, §11.5); `wurzel_fsize_k5601_8x512: 352` — der Bau bricht ab, wenn `swplo` < Größe der Wurzel |

Eine eigene Variante (z. B. Wurzel in rk0: `mutos_1216 kern` mit den Gerätewörtern, §11.4) ist eine Zeile `variante_…` plus Patchzeilen, dazu `VARIANTEN`/`LADEDISKETTEN` wie in A9 Weg 1.  **Eine Datei ändern** (z. B. das Menü `OS.INIT`):
`unzip …boot_udos.zip -d meine_lade`, Datei unter `meine_lade/dateien/` tauschen (Angaben im `.fileinfo`), `bau_ladediskette.py meine_lade neu.hfe --laufwerke …`.

**Von Hand im Gast** (zwei Laufwerke): von einer fertigen Ladediskette in A: `FORM.B` → `1` → `Y`, dann `COPY.B V 0 TO 1` (§9.13 Verfahren A).  Die Kopie trägt dieselbe Konstante wie die Quelle.
**Von Hand offline:** Sektorkopie samt Nachspann mit dem DiskTool und Patch des Bytes (§9.13 Verfahren B, Python-Beispiel dort) — durch die Pipeline ersetzt.

Container immer `.hfe` (der DMK-Schreiber macht bei FM falsche CRCs, §9.9).  Auf eine echte Diskette: `.hfe` mit dem Greaseweazle schreiben.

## A7. Wurzeldiskette bauen

**Mit der Pipeline** (Quelle: `disks/a5120_mutos8000/a5120_mutos8000_m8k_root.zip` = `dateien/` mit `.fileinfo` und `wega-dateiangaben.txt` für Geräteknoten,
`bauangaben.yaml` (`inodes 104`, `bloecke 250`), `zylinder0.bin` (Etiketten `ERMAP`/`VOL1MUTOS`)):

```sh
python3 -I tools/mutos8000/bau_aus_archiv.py disks/a5120_mutos8000/a5120_mutos8000_m8k_root.zip wurzel.hfe                     # FM (MF3200)
python3 -I tools/mutos8000/bau_aus_archiv.py disks/a5120_mutos8000/a5120_mutos8000_m8k_root.zip wurzel_mfm.hfe --laufwerke k5601 # MFM (K5601)
```

**Datei ändern:** `unzip …m8k_root.zip -d meine_wurzel`, unter `meine_wurzel/dateien/` tauschen (z. B. `etc/passwd`, `etc/ttys`, `.profile`; Rechte/Eigentümer/Zeit im `.fileinfo`,
eine neue Datei braucht ein eigenes `.fileinfo`, ein neuer Geräteknoten eine Zeile in `wega-dateiangaben.txt`), `bau_aus_archiv.py meine_wurzel neu.hfe [--laufwerke k5601]`.
Ablauf im Skript: `create --fs mutos8k_26x128_fm|mutos8k_26x128_mfm --inodes 104 --blocks 250`, `boot-put zylinder0.bin`, `put`, `check --full`, unabhängige Prüfung.

* **`bloecke: 250` ist die Swap-Grenze, keine Platzfrage:** der Kernel lagert auf rk2 ab Block 250 aus (`/dev/swap` = 4,2).  Ein größeres Dateisystem wird beim Benutzen
  überschrieben (so geschehen: `/bin/sh` zerstört, §4.8).  Der Bau bricht ab, wenn ein Block ≥ `s_fsize` belegt wäre.  Swap verlegen: §11.5 (`swplo`/`nswap` im Kernel bei Datei-Offset 0x8884/0x8888).
* **Von Hand offline:** `k1520disktool create wurzel.hfe --fs mutos8k_26x128_mfm --inodes 104 --blocks 250`, `boot-put` von Zylinder 0, `put` eines Ordners mit `.fileinfo`/
  `wega-dateiangaben.txt` (genau das tut das Skript; der historische Erstbau aus `M8KROOT` + DISK-ROOT: `bau_wurzel.py`, §4.8).
* **Im Gast** lässt sich eine Wurzel nur bedingt bauen: `FORM.M` + `mkfs /dev/rkN 250` (A5) ergeben das leere Dateisystem, Geräteknoten legt `mknod` an, Dateien `cp` —
  dazu muss eine laufende Wurzel schon da sein.  Nicht ausprobiert.

## A8. Datendisketten bauen

* **Pipeline:** `python3 -I tools/mutos8000/bau_aus_archiv.py disks/a5120_mutos8000/a5120_mutos8000_best_cmd.zip cmd_mfm.hfe --laufwerke k5601` (ebenso `usr`, `bin`, `cc1`, `cc2`; cc1/cc2 = Inhalt von DISK-CC1/-CC2 unverändert auf 26 × 128, beide für `/usr`, nur eine zugleich — die vollständige Kette steht auf `usr`);

* **Datei ändern / hinzufügen:** Archiv auspacken, unter `dateien/` ändern, `bau_aus_archiv.py <ordner> neu.hfe`.  Ist die Diskette voll (cmd: 213 KB von 235), bricht `put` ab.

## A9. Ladediskette patchen: Anzahl und Typ der Laufwerke

**Ein Byte entscheidet:** die UDOS-Initialisierung der Ladediskette führt `LD A,<k> / AND D / LD (0FCAH),A` aus (Zylinder 2, Sektor-ID 1, Offset 120 = `3EH`, Offset 121 = `<k>`).
`[0FCAH]` hält **2 Bit je Laufwerk**, A: in Bit 0–1, B: 2–3, C: 4–5, D: 6–7: `0` = nicht vorhanden, `1` = 40 Spuren MFM (K5600.10), `2` = 77 Spuren **FM** (MF3200),
`3` = 77 Spuren **MFM** (K5601).  `D` ist die Maske der beim Start antwortenden Laufwerke — ein eingetragenes, aber fehlendes Laufwerk fällt dadurch heraus (gemessen:
`FFH` mit drei Laufwerken startet ohne Meldung).  Dieselbe Tabelle benutzen UDOS, `FORM.*`, `COPY.*` und `mutos_io`; eine zweite Einstellung gibt es nicht (§9.13).

| Wert | A: | B: | C: | D: | Bemerkung |
|---|---|---|---|---|---|
| `2AH` | FM | FM | FM | — | Auslieferung (`…_mf3200.hfe`) |
| `AAH` | FM | FM | FM | FM | vier MF3200 (nicht gebaut; im Debugger erprobt) |
| `FFH` | MFM | MFM | MFM | MFM | `…_k5601.hfe` |
| `FEH` | FM | MFM | MFM | MFM | `…_mf3200_k5601.hfe` |
| `15H` / `55H` | 40 Sp. | 40 Sp. | 40 Sp. | (40 Sp.) | K5600.10 — nicht erprobt; Wurzel und Daten bräuchten 40-Spur-Disketten |

Wert = Σ Typ(n) · 4ⁿ (n = 0 für A:).  Mehr als vier Laufwerke kennt die Tabelle nicht (Rückseiten als Laufwerke 4–7: der Nukleus weist sie mit `C2` ab, §11.7).

**Drei Wege:**
1. **Pipeline (dauerhaft):** in `tools/mutos8000/bauangaben_ladediskette.yaml` eine Zeile `variante_<name>: fm|mfm <Wert>` (Aufzeichnung der Ladediskette selbst,
   also des Laufwerks A:), dieselbe Zeile in `bauangaben.yaml` des Archivs (`archiv_erzeugen.py --art ladediskette --force` legt die Vorlage hinein), `VARIANTEN` in
   `bau_ladediskette.py` und — für eine eingecheckte Diskette — `LADEDISKETTEN` in `bau_alle.py` ergänzen; dann `bau_ladediskette.py … --laufwerke <name>`.  Das Skript patcht nur,
   wenn das Muster `3E ?? A2 32 CA 0F` genau einmal vorkommt und der alte Wert `2AH` ist.
2. **DiskTool (eine einzelne Diskette):** Sektor Zylinder 2, Sektor-ID 1 lesen, Offset 121 ändern, zurückschreiben (Python-Beispiel §9.13 Verfahren B, `DiskTool.open_raw`,
   `sector_data`/`sector_write` — Sektor-**Index** 0 = ID 1).  Nur an einer Kopie.
3. **Debugger (nur ausprobieren, nichts auf der Diskette):** nach dem Start `e 0x0FCA 0xAA` (bzw. `0xFF`, `0xFE`), vor `FORM.*` bzw. vor dem `mount`.

**Nicht über `[0FCAH]` einstellbar:** Wurzel-Laufwerk (rk2), Swap-Gerät und -Bereich, Sektorgröße (26 × 128 fest in `mutos_io`) — dafür §11 (Stellschrauben-Tabelle §11.8, Patchwerkzeug `tools/mutos8000/mutos_patch.py`).  **Wurzel in A: geht ohne Patch** über die Zuordnungsmaske von `mutos_io` (rk-Nummern je Laufwerk eintippen, §11.4).

## A5b. tar-Disketten im MUTOS-Layout (DiskTool lesen und schreiben, 2026-10-25)

**Profilnamen (2026-10-26):** Schema `mutos8k_<Sektoren>x<Bytes>_<fm|mfm>`, tar mit Vorsatz `tar_`.  Altnamen: `mutos8k_fm`→`mutos8k_26x128_fm`, `mutos8k_mfm`→`mutos8k_26x128_mfm`, `mutos77`→`mutos8k_8x512_mfm`, `mutos80`→`mutos8k_8x512_mfm_80`, `tar_mutos8k_{fm,mfm}[_leer]`→`tar_mutos8k_26x128_{fm,mfm}[_leer]`; die alten Namen gelten als `aliases:` in `data/formats.yaml` weiter (`FsCatalog::find`), erscheinen aber in keiner Liste.

Das V7-`tar` (liegt auf der Diskette `bin`) schreibt **nackt auf das Rohgeraet** `/dev/rrkN` (`tar cvf /dev/rrk0 …`, `tar tvf`, `tar xvf`; immer `f` mit Geraet, relative Namen, `pwd` im Pfad).
Der Strom liegt in 512-B-Bloecken der Blockabbildung §4.6.3 (ab Zylinder 1, Verschraenkung 2, Spurversatz 6): **494 Bloecke = 252 928 B je Diskette**, Zylinder 0 bleibt unberuehrt.
Ein Archiv ueber 494 Bloecke haengt (kein Mediumende); Mehrdisketten gehen nur ueber `dd`: `tar cf - … | dd of=/dev/rrk0 bs=512 count=494`, Folgediskette `skip=494` (zurueck: `(dd if=/dev/rrk0 bs=512 count=494; …; dd …) | tar xvf -`).

**DiskTool:** `tar_mutos8k_26x128_mfm` (K5601, Format `udos_ss77`), `tar_mutos8k_26x128_fm` (8″, `mf3200_26x128`), je mit `_leer`.  Dieselben Wege wie `tar720`:

```
k1520disktool tar-satz mutos1.hfe mutos2.hfe [-l | --to ordner]       # Layout wird am ersten Abbild erkannt
k1520disktool tar-satz-neu --format tar_mutos8k_26x128_mfm satz.hfe --put a.bin --put b.bin   # -> satz1.hfe, satz2.hfe zu je 494 Bloecken
k1520disktool tar-satz-save mutos1.hfe mutos2.hfe --put neu.bin --rm alt.bin [-o basis.hfe]
k1520disktool create leer.hfe --fs tar_mutos8k_26x128_mfm_leer               # (…_fm_leer: 8″ FM); --format tar_mutos8k_26x128_mfm auch bei tar720_leer-Weg
k1520disktool tar-formate                                             # nennt beide Profile mit 252928 B
```
In der Oberflaeche erscheinen sie in *Neue tar-Diskette/Satz* (Formatliste) und *Neue Diskette* (`…_leer`); Oeffnen/Speichern wie bei jeder tar-Diskette.
Container: `.hfe`/`.dmk`/`.img`/`.cqm`/`.td0`/`.imd`; ein `.img` ist immer MFM (Aufzeichnungsverfahren steht nicht darin).  Neue Disketten tragen im Datenbereich **Nullbloecke**
(eine nie beschriebene E5-Diskette liest MUTOS-`tar` nicht sauber zu Ende), Zylinder 0 bleibt formatiert E5.

**Unter MUTOS im Emulator abgenommen** (Wächter `cli_mutos8000_tar_disktool_geschrieben`): DiskTool-Einzeldiskette (`libc.a` 72 KB) — `tar tvf`, `tar xvf` und `cmp` gegen das Original; DiskTool-Satz aus
zwei Disketten ueber `dd | tar xvf - d.o`, die Datei liegt zu 3 Bloecken hinter der Grenze, `cmp` gleich.  Umgekehrt liest das DiskTool von MUTOS geschriebene Einzeldisketten und Saetze
(Fixtures `mutos8000_tar_*.dmk`, Wächter `TarMutos.*`).
**Fallen im Gast:** eine Diskette eines Satzes ist kein abgeschlossenes Archiv — `tar` meldet am Ende `Tar: tape read error` (es liest 8 Bloecke ueber das Mediumende; Inhalt davor ist vollstaendig);
**vor dem Tausch einer Diskette (`mount A …` im Debugger) `sync`**: MUTOS puffert Schreibzugriffe ueber `/dev/rkN` und schreibt sie sonst auf die NEUE Diskette (so entstanden die scheinbar falsch gelesenen
Sektoren des offline gepackten Abbilds; DiskTool und Emulator waren fehlerfrei).  Festlegungen: `doc/merkposten/tar_satz.md` Nr. 17.

## A5c. 8 × 512 (DISK-Satz): UNIX-Dateisystem, tar und der Swap-Fehler im 8 × 512-`mutos_io` (2026-10-26)

**Ergebnis in Kürze:** das UNIX-Dateisystem `mutos8k_8x512_mfm` ist vollständig (lesen, schreiben, `create`, `fsck`) und die Blockabbildung stimmt für das, was `mutos_io` (8×512) auf der Platte ablegt;
tar-Disketten und -Sätze im 8×512-Layout gibt es als `tar_mutos8k_8x512_mfm[_leer]`.  Beim Messen fiel ein **Fehler im 8×512-Patch der Ladediskette** auf, der behoben ist (unten); ohne ihn läuft `tar` nicht.

**Gegenprobe des Dateisystems am Emulator** (Ladediskette `k5601_8x512`): (a) eine vom DiskTool angelegte Diskette (`create --fs mutos8k_8x512_mfm`, `put` von bin/ed und d/od) liest MUTOS (`ls -l`, `cmp` gegen die Originale);
(b) MUTOS schreibt darauf (`cp` von adb 27 770 B = mit Indirektblock, `mkdir`, `cp`, `rm`, `echo > f`, `sync`) und das DiskTool liest alles zurück, `check --full` ohne Befund (Fixture `mutos8000_8x512_geschrieben.td0`, Wächter
`MutosFs.M8x512_VonMutosGeschriebenesLiestDasDiskToolUndFsckIstSauber`).  Eine Lücke gab es nur beim Anlegen: auf der 80-Zylinder-Diskette (`mutos8k_8x512_mfm_80`) bekam das Dateisystem 632 Blöcke, der Kernel lehnt aber Block ≥ 608
ab (`rkstrategy`, §11.2) — `create` begrenzt es jetzt ohne `--blocks` auf 608 (`MutosFs.M8x512_NeueDisketteNimmtDieBlockgrenzeDesKernelsEin`).

**Layout von tar (am Emulator gemessen).**  MUTOS-`tar cvf /dev/rrk3 …` schreibt den V7-Strom nackt ab **Block 0 des Rohgeräts = Zylinder 1, Sektor-ID 1**, dann linear: Block n = Zylinder 1 + n/8, ID n mod 8 + 1 (keine Verschränkung,
kein Spurversatz — es ist dieselbe Folge wie beim UNIX-Dateisystem, `WegaSpaceDev` ab `data_start`).  Kapazität des Rohgeräts: **608 Blöcke = 311 296 B** (76 Zylinder × 8; der Kernel lehnt Block ≥ 608 ab, auch auf einer
80-Zylinder-Diskette, deshalb gibt es kein `_80`-Profil); Zylinder 0 (26×128) bleibt unberührt.  Ohne `b`-Angabe: Strom = Kopf + Daten + 2 Nullblöcke.  Über das Ende hinaus meldet `tar` sauber **`Tar: tape write error`**
(anders als beim 26×128: dort hängt es).  Linux-Gegenprobe: Strom aus den Sektoren mit der Formel dekodiert → `tar tvf` zeigt alle Dateien, bytegleich (`rawlin.py`-Prinzip; als Test die EIGENE Formel in `test_tar_mutos.cpp`).
Neu eingelegt (nach `sync`) liest `tar tvf` alles wieder.  **Mehrere Disketten** wie beim 26×128 nur über `dd`: `tar cf - … | dd of=/dev/rrk3 bs=512 count=608`, Folgediskette `skip=608`; Rückweg
`(dd if=/dev/rrk3 bs=512 count=608; echo … >/dev/console; dd if=/dev/console of=/dev/null count=1; dd if=/dev/rrk3 bs=512 count=608) | tar xvf - …` — Diskette tauschen, bei der Aufforderung eine Zeile (`x` + Enter) tippen;
eine Datei über die Grenze (`mnt/bin/tar`, 17 000 B, Block 586–620) kam `cmp`-gleich an.  Eine Diskette eines Satzes ist KEIN abgeschlossenes Archiv (`tape read error` am Ende, Inhalt davor vollständig).

**DiskTool:** Profile `tar_mutos8k_8x512_mfm` und `…_leer` (Format `mutos_ss77`, `unix_layout: mutos8k_512` für `type: tar` → `FsProfile::mutos8k_linear`, `TarSpaceQuelle` nimmt dann `WegaSpaceDev` statt `Mutos8kDev`).  Erkennung wie
beim 26×128: Vorprobe vor den Dateisystemen der Geometrie, nur mit gültigem tar-Kopf bei Block 0 (bzw. Datenbereich ganz Null für `_leer`); ein `wega_mutos`-Dateisystem derselben Geometrie geht vor und bleibt, was es ist (DISK-ROOT/CC1/CC2/CMD
werden nie zum tar, Wächter `cli_dt_mutos_8x512_erkennung*`).  Alle Container außer `.cqm` (gemischte Geometrie: Zyl. 0 = 26×128).  Ein tar-Satz über mehrere Abbilder, `create`, `tar-satz-neu`, `tar-formate`, GUI-Formatliste unverändert.

**Der Fehler (behoben): halbe Schluss-Sektoren im Swap.**  Die Swap-Aufträge des Kernels sind Vielfache von 256 B (z. B. 0D00H = 3328 B = 6,5 Blöcke); beim 26×128 (128-B-Sektoren) ging das auf, beim 8×512 bleibt ein halber Sektor, und die Schleife
von `mutos_io` (`9893`: Rest − 0200H, **nur Test auf Null**) lief mit Rest 0100H ins Negative, las weiter, der Zylinder lief davon, der Treiber meldete `er=1,305` (Zylinder stimmt nicht) und der Kernel starb mit
`panic: IO err in swap`.  Ausgelöst wird es, sobald ein vierter Prozess Platz braucht — `tar` ruft `pwd` (fork), `sh | dd | tar` ebenso.  Der Grund stand in §11.2 als Vorbehalt (2); im bisherigen Wächter (`ls`, `cat`, `mount`) kam
kein Swap vor.  **Behebung** (`mutos_patch.py io-8x512`, achte Patchstelle, 6 Byte bei `98C0`): `AF ED 52 7C B5 28` → `B7 ED 52 38 28 28`, d. h. nach `SBC HL,DE` beendet auch ein **Übertrag** (Rest < 0200H) den Auftrag; der letzte Sektor wird ganz
gelesen/geschrieben (im Staging-Puffer ist Platz; beim Schreiben landen 256 B Restinhalt im Swap, unschädlich).  `…_boot_udos_k5601_8x512.hfe` ist neu gebaut (`bau_ladediskette.py`).  Gemessen: `tar cvf` über 34 Dateien, Satz über zwei
Disketten und Rückweg laufen.  Wächter: `test_patchliste_…`/`test_eingecheckte_ladediskette_…[k5601_8x512]` (Soll-Bytes unabhängig), `cli_mutos8000_tar_8x512_disktool_geschrieben`.

**Zweite Falle: `pwd` von 1987.**  `tar` startet `/bin/pwd` zuerst; DISK-ROOT trägt die `pwd` von 1987, die `/` ausgibt und nie zurückkehrt (§10.1) — der Aufrufer (`sh`, `tar`) wartet ewig.  Mit der `pwd` von 1986 läuft es.

**td0 oder Eigenbau? — beides, je nach Disk.**  `…_cc1.td0`, `…_cc2.td0` (78 Spuren) und die Ladediskette lassen sich unverändert einlegen; **`…_cmd.td0` nicht**: 83 Spuren (6 Spuren Altbestand dahinter), ein K5601 erreicht 80
(`mount: Diskette hat 83 Spuren mit Daten, Laufwerk 'K5601' erreicht nur 80`), außerdem nur 512 B frei.  **`…_root.td0`** läuft, hat aber die hängende `pwd`.  Deshalb baut `tools/mutos8000/bau_8x512.py` (auch von `bau_alle.py` gerufen) aus den TD0-Originalen
`disks/a5120_16_MUTOS/a5120_mutos8000_root_8x512.hfe` (DISK-ROOT, nur `bin/pwd` durch die 1986er aus `best_cmd.zip` getauscht) und `…_cmd_8x512.hfe` (dieselben 19 Dateien auf sauberem 77-Zylinder-Medium, 480 Blöcke, 77 KB frei).
Wächter `test_8x512_wurzel_und_befehle_sind_die_td0_originale_mit_der_alten_pwd`.  Leere 8×512-Datendisketten: `create --fs mutos8k_8x512_mfm` (UNIX) bzw. `…tar_mutos8k_8x512_mfm_leer`; eine Datendiskette aus Archiven wie beim 26×128 wurde nicht gebraucht.

**Ablauf unter dem 8×512-System** (Laufwerke: A: tar-Diskette, B: `cmd_8x512` auf `/mnt`, C: `root_8x512`, D: zweite tar-Diskette), so im Wächter getippt:

## A5a. Mehrbenutzerbetrieb und zweites Terminal (gemessen 2026-10-25, Wurzel `…_root_mfm`, Ladediskette `k5601`)

`/etc/init` ist ein V7-`init`: Einzelbenutzer-Shell auf der Konsole, nach deren Ende `/etc/rc` (gibt es auf der Wurzel nicht; fehlt es, geht es trotzdem weiter) und je ein `getty` für jede in `/etc/ttys` freigegebene Zeile. **Es gibt kein `init 2`.**

1. Wie gewohnt booten, als `root` anmelden, Datendisketten einhängen (`/etc/mount /dev/rk0 /usr`, `/etc/mount /dev/rk1 /mnt`).
2. **Einzelbenutzer-Shell mit ^Z verlassen** (nicht ^D, nicht `exit`: ^D kommt an, ist aber nicht das EOF-Zeichen dieses Treibers; `exit` beendete die Shell im Versuch nicht; ^C unterbricht, DEL nicht). Auf dem Schirm erscheint `login:`; die Einhängungen bleiben.
3. Zweites Terminal: `/dev/tty1` (Gerät 0,1; Zeile `12tty1` in `/etc/ttys` — die Wurzel liefert sie schon freigegeben) ist **SIO A33 Kanal A = „DFÜ/V.24“** (Ports 50H/51H, `k1520_serial_*` Index 0). Dort Telnet-Server (oder RFC 2217, Datei) einstellen und starten, mit einem Telnet-Client verbinden: `getty` meldet sich erst **nach** ^Z mit `login:`; Anmeldung als `root`, `.profile` (PATH mit `/mnt/bin`, `/usr/bin`) läuft, `who` zeigt `console` und `tty1`, `ps` (ohne Argument; `-ax`/`ax` werden als Terminal-/Benutzername gedeutet) zeigt beide Shells.
4. Baud/Format meldet der Gast nicht (`baud_nenn` 0, `format_gueltig` falsch) — es läuft trotzdem; die Ausgabe trägt `CR NUL LF` (Wagenrücklaufverzögerung des Treibers), ein Telnet-Client zeigt es richtig.

5. **Terminalweg ohne Telnet-Programm (gemessen 2026-10-25):** `p8000emu --mode terminal` (Kernmaschine `p8000-terminal`, Originalterminal + K7673) als Telnet-**Client** an den Server der DFÜ/V.24 (`k1520_serial_*` Index 0 der Terminaleinheit, in der GUI *Maschine ▸ Verbindung zum Rechner…*). Ergebnis: Einschaltmeldung `ADM31/9600 baud`, nach ^Z an der Konsole `login:`, Anmeldung als `root`, `ls /`, `cat`. **Strg-Kombinationen kommen an** (Terminal-Strg → K7673 → Firmware → Telnet → SIO): ^Z beendet `cat` (EOF), ^C bricht es ab. Nicht geprüft: ^S/^Q, die Bildschirmtastatur mit der Maus, das Fenster selbst (nur die Kernbindung beider Instanzen im Gleichschritt, je 50 000 Takte A5120 gegen 46 080 Z8-Takte). ## 3. Beobachtungen am Kernel (mit `M8KROOT` als Root)

Zeiten in Maschinentakten; „c186.79M“ = Takt 186 790 000 nach Start.

1. **Platte wird gelesen, ohne Fehler:** Lesetransfers auf Zyl. 1, Kopf 0 mit aufsteigenden Sektornummern 9, 10,
   11 … (Anforderung ab Sektor 9 = Block 1 bei 8 Sektoren je Block); die letzte Plattenaktivität und der letzte
   Moduswechsel liegen bei c186.79M, ≈ 1 Mio. Takte nach `r`.
2. **Danach nur noch Uhr-Interrupts:** Vektor `02` alle ≈ 49 000 Takte (8 113 in 400 Mio. Takten), nichts anderes.
   Der U8001 steht bei `<<1>>%000A` in `JR %000A`.  Tastendrücke (` root\r`) erzeugen **keinerlei** Ereignis in
   `emlog`.
3. **Das ist Prozess 1, nicht der Kernel-Leerlauf.**  `<<1>>%0000`:
   ```
   %0000  LD R0,#%0010      ; Pfad "/etc/init" bei %0010
   %0004  LD R1,#%000C      ; argv bei %000C = { %0010, 0 }
   %0008  SC #%0B           ; exec
   %000A  JR %000A          ; exec fehlgeschlagen -> Endlosschleife
   ```
4. **`exec` scheitert mit ENOTDIR (20):** Der Systemaufruf kehrt nach ≈ 4 500 Takten **ohne Plattenzugriff**
   zurück.  `u_error` (`%FC13`) wird bei `%375C` auf `0x14` geschrieben, unmittelbar nach
   `LD R2,%0006(R13); AND R2,#%F000; CP R2,#%4000; JR Z,…` (`%374E`–`%375A`) — der Kernel prüft den
   Modus-Typ des gerade aufgelösten Verzeichnis-Inodes auf `IFDIR = 0x4000`.
5. **Der Wurzel-Inode:** `rootdir` = `[%8DC6]` = `%907A`, gesetzt bei c186.802M durch `%06CC` (iget).  Inhalt im
   Speicher: `0003 0402 0002 83FE 0010 0000 0002 0000 0120 0000 4600 …` — als V7-Inode gelesen:
   `i_dev = 0402` (Major 4 = Floppy, Minor 2 = rk2 ✓), `i_number = 2`, **`i_mode = 0x83FE`** (Typ 0x8000),
   `nlink = 0x10`, `size = 0x120`.  Typ 0x8000 ist kein Verzeichnis → ENOTDIR.
6. **Der Emulator liefert bitgenau, was im Abbild steht:** dieselben Bytes liegen in `M8KROOT.TD0` an Zyl. 1,
   Sektor-ID 17, Offset 64.  Plattenzugriff und Kernel-Rechnung sind in sich stimmig.
7. Eine Syscall-Spur des U8001 (`s` mit `cpu u8000`) zeigt den Pfad: Eintritt `%030E`, Sprung über die Tabelle
   `CALL @R4` nach `%087A`, Namensauflösung ab ≈ `%3520`, Zeichenholer über Funktionszeiger (`CALL @R2` →
   `%39BA` → `%04CC`), Fehler bei `%375C`, Austritt über `%03C2` (`OUT %0080` = A33) und `IRET`.

## 4. Diskettenformat-Befunde

### 4.1 Wie der U880-Treiber Blöcke auf Spuren abbildet

* Der Plattentreiber ist der **UDOS-Nukleus-Treiber** (ZVE1 `%0770`–`%08DC`, ZVE2-Leseschleife `%0A1A`–`%0AD2`),
  den `mutos_io` mit einem Anforderungsblock (`IY = %996E`) ansteuert.  Sektor = `(IY+0Bh & 1Fh) + 1`,
  Zylinder = `IY+0Ch`, Zähler `[0FCD]`; Fehlercodes der Schleife: **`44H` = Sektor nicht gefunden**,
  **`45H` = Zylinder stimmt nicht** (Bit 7 gesetzt im Bericht: `0xC4` = oktal `304` — das ist das `er=0,304`
  des Kernels).
* `mutos_io` rechnet die Anforderung des Kernels selbst um (`%9840`–`%9966`): Konstanten **26** (`1AH`) und
  **`0D00H`** (= 26 × 128), Schrittweite **6** (`ADD A,06H` mod 26 bei `%992C`).  Die Umrechnung ist also auf
  **26 Sektoren zu 128 B mit Interleave 6** ausgelegt, mit einem Pufferzähler in Einheiten zu 128 B
  (`LD DE,0080H`, `%98B3`).
* Ergebnis für Block 1 (`bn=1`): **Zylinder 1, Sektor 9** — ein Wert, der auf einer 8×512-Spur nicht existiert.

### 4.2 DISK-Satz (8×512)

* Gültiges UNIX-Dateisystem (DiskTool: `fsck` sauber, Wurzel lesbar), aber Block 1 = Zyl. 1 Sektor 2.
* Mit dieser Ladediskette: `err on dev 4/2  bn=1 er=0,304` (viermal), dann `panic: iinit`.  Der Treiber verlangt
  Sektor 9 auf einer Spur mit den Sektoren 1–8 (Fehlercode `44H`).  Die Diskette ist lesbar (`disk verify`:
  0 CRC-Fehler); sie gehört **nicht zu dieser Treiberfassung**.  *Umbau von `mutos_io` auf 8×512 (gemessen lauffähig): §11.2.*

### 4.3 M8K-Satz — Überblick (Befund 2026-10-23, DiskTool-Zweig)

Die ursprüngliche Lesart „26×128, Interleave 6, nur ungerade IDs belegt, 80 Zylinder" ist **überholt** (Einzelheiten §4.6):

* **CMD und USR sind 8″-FM-Disketten** (77 Zylinder × 26 × 128) mit gültigem UNIX-Dateisystem. Die Blöcke liegen NICHT in der
  linearen Sektorfolge, sondern mit **Verschränkung 2 und einem Spurversatz von 6 Sektoren** (§4.6.3).  „Nur ungerade IDs tragen Daten"
  war ein Zufallsbild des *ersten* Zylinders (Block 0 = IDs 1,3,5,7 / Block 1 = 9,11,13,15 / Block 2 = 17,19,21,23); die geraden
  IDs tragen die Blöcke 3 ff. (Block 3 = IDs 25,2,4,6).
* **BIN ist ein gewöhnliches `mutos77`** (5¼″ MFM, Zyl. 1–76 × 8 × 512, Block n = Zyl. 1 + n/8); nur sein Zylinder 0 ist 26×128.
* **ROOT ist als Abbild beschädigt** (§4.6.6): in jedem 128-B-Sektor sind alle Bytes ab Offset 1 um **1 Bit nach links verschoben**
  und die **letzten 48 Byte durch eine Fremdtabelle ersetzt**.  Genau das liest der Kernel: Wurzel-Modus `0x83FE` statt `0x41FF`.
  Der in §3 beobachtete ENOTDIR-Fehler ist damit ein **Abbildbefund, kein Emulator- und kein Abbildungsfehler**.
* ROOT hat **80 Spuren** (Zyl. 0–76 je 27 Sektoren zu 128 B, Zyl. 77–79 je 16 Sektoren zu 256 B), nicht „80 × 26 × 128".

### 4.4 Treiber und Abbildung (Rechenaufgabe gelöst)

Aus Treiber (§4.1) und Abbild folgt die eindeutige Abbildung (Formel und Tabelle in §4.6.3); sie passt zu den Konstanten des
Treibers (26 Sektoren, `0D00H` = 26·128, Schritt 6 bei `%992C`) und erklärt „Block 1 → Sektor 9".  Belegt durch Konsistenz des
Dateisystems auf CMD und USR (Wurzel, Baum, Freiliste, 23 `a.out` mit stimmender Größe), nicht durch den Treibercode allein.

### 4.5 Was das für den Emulator-Boot heißt

* `M8KROOT` liefert dem Kernel bitgleich die verschobenen Bytes (Emulator = Abbild, §3.6).  Die Wurzel-Inode ist darin `83FE 0010 …`
  (= `41FF 0008 …` um 1 Bit verschoben); der Kernel prüft `mode & F000 == 4000` und meldet ENOTDIR.
* CMD, USR und BIN sind nicht bootfähig (kein `/etc/init`, keine Wurzeldiskette, CMD nur `etc/clri … mkfs`), aber lesbar.
* Eine **unverändert verwendbare Wurzeldiskette ist aus diesem Satz nicht zu gewinnen**: von jedem Sektor sind nur die ersten ~80 Byte (mit
  1 unbekannten Bit) erhalten, 47 Byte je Sektor fehlen.  **Aus den Resten plus den Programmen von DISK-ROOT lässt sich dennoch eine bootfähige Wurzel
  rekonstruieren** (§4.7.6, §4.8); sie ist keine Wiederherstellung der Original-Diskette.  Offene Fragen §6.

### 4.6 Formatbeschreibung der Disketten

Alle Werte mit eigenen Parsern (`tools/mutos8000/m8k.py`) und dem DiskTool nachgemessen.  Der SCP-Fluss
(`M8K*_TD0.scp`) wurde mit `gw convert --format=ibm.scan --tracks=c=0-79:h=0 <scp> <out>.imd` (venv des Projekts, Greaseweazle 1.23)
in IMD gewandelt und Sektor für Sektor mit der TD0 verglichen: **ROOT: 2127 von 2127 Sektoren gefunden, 0 Abweichungen; CMD 1999/2001,
USR 1996/2001, BIN 634/635 gefunden, alle gemeinsamen Sektoren bitgleich zur TD0** — die TD0-Defekte stammen also von der Diskette

#### 4.6.2 Der Zusatzsektor ID 126 (ROOT, BIN Zyl. 0)

* ROOT: auf **allen 77 Spuren Zyl. 0–76** steht an erster Stelle ein Sektor mit der ID **126** (128 B), danach IDs 1–26.  BIN: nur auf Zyl. 0.
  CMD/USR haben ihn nicht.
* In der **TD0**: Sektorkopf (Zylinder = Spur, Kopf 0, R = 126, N = 0), **Flag `0x40`** (TeleDisk: „Daten ohne ID-Feld", Pseudosektor, siehe
  38a Z. 192), Datenblock normal 128 B; Inhalt wie jeder andere Sektor derselben Spur (`E5 CB…` + Fremdtabelle).
* Im **SCP-Fluss existiert er physisch**: `gw` findet ihn als normalen Sektor mit ID 126 (daher 2127 = 77 × 27 + 3 × 16 Sektoren).
  Er ist also kein TD0-Artefakt, sondern eine echte Adressmarke mit ID 126 — der Treiber (IDs 1–26) fasst ihn nie an.
* **DiskTool**: Pseudosektoren liegen nicht im Medium, werden aber in `SourceInfo::pseudo` mitgeführt und beim Zurückschreiben einer `.td0`
  wieder eingesetzt.  Round-Trip an BIN (`put` einer Datei → neue `.td0`): 635 von 635 Sektoren vorhanden, nur die geänderten Blöcke
  weichen ab, ID 126 bleibt erhalten.  (ROOT selbst lässt sich nicht öffnen.)

#### 4.6.6 M8KROOT im Detail

**(a) Fremdtabelle.**  Die **letzten 48 Byte (Offset 80–127) jedes 128-B-Sektors** sind auf allen Spuren Zyl. 0–76 und bei allen 27 Sektoren (IDs 126, 1–26)
**identisch**; die 27 × 48 = 1296 Byte bilden, in der Reihenfolge der Sektoren der Spur 126, 1, 2, …, 26 gelesen, einen fortlaufenden Text, dessen Zeilenende
mitten im Sektor liegt: ASCII-Liste von Diskettenformaten („`rne G2 System - DSDD 48 tpi 5.25"`", „`OSB6`·Osborne 1 + Osmosis 48 tpi", „`OSB9`·Osborne Executive w/Z3 –
DSDD 96 tpi", „`OTR1`·Otrona Attache", „`PEG1`·Pegasus Data Logger", „`TEL4`·Tele…", „`TRS1`·TRS-80 Model 1, Omik…", „`TRS8`", „`TRSA`", „`VEC1`·Vector 4",
„`PIE1`·Pied Piper", „`PRO2`·Prog…", „`SAG2`·Sage IV", „`SEE1`·Seequa Chameleon", „`SHL1`·Shelp MZ-80", „`WAV1`·Wave Mate Bullet", „`XER2`·Xero…"), je Eintrag
Kennung (4 Zeichen) + 2 Byte (vermutlich Prüfwert) + `00 00` + Name.  Die Tabelle gehört nicht zu MUTOS; an Stellen ohne Nutzdaten (Zeilen mit Nullen) ist sie
am deutlichsten.  Von jedem Sektor bleiben **80 Byte** (62,5 %), 47–48 Byte (37,5 %) sind überschrieben.  Gemessen als „längstes gemeinsames Suffix über alle
Spuren ab Zyl. 2": 48 Byte für alle 27 IDs.

**(b) 1-Bit-Verschiebung.**  In den ersten 80 Byte jedes Sektors ist **Byte 0 unverändert, jedes weitere Byte um ein Bit nach links verschoben**
(`beob[i] = (orig[i] << 1 | orig[i+1] >> 7) & FF` für i = 1…79; das höchste Bit von `orig[1]` ist verloren).  Beispiele:

* Fuellung `E5 E5 E5…` erscheint als `E5 CB CB CB…` (`E5 << 1 | 1 = CB`).
* Zyl. 0 ID 5/7: `C5 D9 D4 C1 D7 40` („ERMAP") erscheint als `C5 B3 A9 83 AE 80`; `E5 D6 D3 F1 D4 E4 E3 D6 E2 40` („VOL1MUTOS") als `E5 AD A7 E3 A9 C9 C7 AD C4 80`.
* Superblock (Sektor ID 9): gelesen `001E 0000 01F4 0040 000000C8 000000C2 …` → `000F 000000FA 0020 00000064 00000061 …` (Freiliste Schritt 3 wie CMD).
* Wurzel-Inode (Sektor 17, Offset 64): gelesen `83FE 0010 0000 0002 00000120` → `41FF 0008 0000 0001 00000090`; Modus `41FF` und gid 1 sind exakt die der CMD-Wurzel.
* Inodes 3/5/7 (Offset 0): gelesen `41FE 0004 0000 0002 000001A0` → `41FF 0002 0000 0001 000000D0`; die geradzahligen Inodes 4/6/8 (Offset 64) zeigen dasselbe
  Bild (`83FE …`).  Inodes 9 ff. sind frei.
* **Wo es gilt:** alle 128-B-Sektoren von ROOT (Nutz-, Frei- und Zyl.-0-Sektoren) in Offset 1–79.  **Wo nicht:** Offset 0 (unverändert) und Offset 80–127 (Fremdtabelle,
  ebenfalls unverschoben als ASCII lesbar).  **BIN**: nur Zyl. 0 (26 × 128) ist so verschoben; die 8 × 512-Spuren ab Zyl. 1 sind in Ordnung.  CMD/USR: nirgends.
* Folge: aus ROOT lassen sich Offset 0–79 wiederherstellen (bis auf das verlorene Bit 8 jedes Sektors, aus dem Kontext meist ableitbar), Offset 80–127 nicht.
  Vermutete Ursache (**nicht belegt**): ein Schreibvorgang mit 1 Bit Phasenversatz nach dem ersten Datenbyte, der nach ~80 Byte endete, sodass der Rest
  der älteren Beschriftung (die Tabelle) stehen blieb.  TD0 und SCP-Fluss (zwei unabhängige Dekodierer: TeleDisk 2011, Greaseweazle 2026) liefern **bitgleich dasselbe**.
  Der SCP-Fluss wurde nicht mit dem BitCodec des Projekts dekodiert (siehe §6).

**(c) Geometrie von ROOT:** 80 Spuren: Zyl. 0–76 je 27 Sektoren (126, 1–26) zu 128 B, **Zyl. 77–79 je 16 Sektoren zu 256 B** (IDs 1–16) — kein 80 × 26 × 128.
Belegt sind Zyl. 1–60 (Zyl. 61–76 reine E5-Füllung).

#### 4.7.6 Was auf M8KROOT noch lesbar ist (Befund 2026-10-23)

**Verfahren (Skripte `tools/mutos8000/`, `m8kroot_lesen.py`).**  Die Sektoren von `M8KROOT` werden mit der Abbildung von §4.6.3 (`Mutos8kDev`) zu 512-B-Blöcken
zusammengesetzt und jeder 128-B-Sektor zurückgeschoben: Byte 0 roh, für i = 2…79 `o[i] = s[i] >> 1 | (s[i-1] & 1) << 7`; bei Byte 1 ist das oberste Bit
unbekannt, Bytes 80–127 sind verloren.  Daraus folgen die Grenzen:

* Von jedem 128-B-Sektor sind **80 Byte** brauchbar.  Ein Verzeichnissektor trägt 8 Einträge zu 16 B, lesbar sind nur die Einträge **0–4**; die Einträge 5–7 fehlen samt Inodenummer.
* **Inode-Tabelle:** je 128-B-Sektor zwei Inodes.  Der **erste (Sektoroffset 0)** ist bis Byte 79 lesbar, also vollständig (13 Adressen, Zeiten), nur das **oberste Bit von Byte 1, das ist
  das Bit `0200` im Modus**, ist verloren (`0575` ist `0775`).  Der **zweite (Offset 64)** liefert nur Modus, nlink, uid, gid, Größe und **die erste Blockadresse** (16 B); Zeiten und
  die übrigen Adressen fehlen.  Das reicht für Gerätedateien (die Gerätenummer steht in der ersten Adresse), nicht für Dateien über 512 B.
* Die Inode-Liste hat `s_isize` 15 → **104 Inodes**; was ab Inode 105 gelesen wird, sind Datenblöcke, kein Inode.
* Zurückgeschoben: `s_isize` 15, `s_fsize` 250, 44 belegte Inodes (2–8, 66–98, 100–102, 104; Inode 1 unbenutzt, 99 und 103 frei), Wurzel-Inode 2 `040777`, uid 0, gid 1.

**Fazit.**  Lesbar und bytegenau überprüfbar sind alle Textdateien, die ersten 320 B bis 3,2 KB jeder Programmdatei (gleich den DISK-ROOT-Fassungen) und die komplette Baumstruktur einschließlich der
Gerätenummern; **nicht** wiederherstellbar sind die Programmrümpfe (ab Offset 80 jedes Sektors), `mount`/`umount` dieser Fassung, die Namen von acht Einträgen (abgeleitet) und die Zeiten der Inodes an Offset 64.
Da die lesbaren Programmbytes **in keinem Fall** von DISK-ROOT abweichen, ist es plausibel, dass die DISK-ROOT-Programme dieselben (oder gleichwertige) sind wie auf `M8KROOT`; **bewiesen** ist das nur für die geprüften Bytes.

## 9. FORM.B, FORM.M, COPY.B, COPY.M der Ladediskette (Befund 2026-10-23)

Alles im Debugger (`k1520dbg --em em256`) nachgespielt; die vier Programme wurden mit `k1520disktool get` aus der Ladediskette geholt und mit `tools/z80_disasm2.py` disassembliert.
Sie sind **UDOS-Programme (Z80, Ladeadresse 4000H)**, die den UDOS-Nukleus über `CALL 0BFDH` (→ `JP 0700H`) benutzen, `FORM.*` zusätzlich die K5122 **direkt** (Ports 10H–18H, CTC 11H).

### 9.0 Korrektur zu §4.7.1
Die Ladediskette ist **durchgehend MFM** aufgezeichnet (Spuren 0–76, je 26 × 128 B MFM), nicht FM.  Ein MF3200 (nur FM) lehnt sie ab
(`Diskette ist MFM-aufgezeichnet, Laufwerk 'MF3200' beherrscht das nicht`); ein MF6400 bzw. K5601 nimmt sie.  Dazu hat sie 3 Altbestandsspuren (77–79, je 5 × 1024 B):
Hinter 77 Zylindern „80 Spuren mit Daten“ — im 77-Zylinder-Laufwerk wird sie deshalb abgewiesen, bis man diese Sektoren löscht (`DiskTool.sector_erase`).

### 9.1 Aufruf und Laufwerkstyp
* `FORM.B` / `FORM.M` fragen `drive ?` (0–3).  **Der Laufwerkstyp kommt nicht aus der Hardware, sondern aus UDOS: `[0FCAH]`** (2 Bit je Laufwerk, Laufwerk n = Bits 2n..2n+1;
  Typ 0 = nicht vorhanden → Fehler `C2`).  Typ 1 = 40 Spuren (`28H`), Typ 2 = 77 Spuren **FM**, Typ 3 = 77 Spuren **MFM** (Nukleus `0868`–`0864`: `BIT 4,D` wählt MFM-Konstanten, CRC-Anfangswert `E295` statt `BF84`).
  Nach dem Boot der Ladediskette steht `[0FCAH]` im Emulator auf `2AH` = ~~alle vier Laufwerke Typ 2 (FM)~~ Laufwerke A:–C: Typ 2, D: Typ 0 (berichtigt §9.4, A9).  UDOS setzt das normalerweise mit `SET DISKCON`.
* `FORM.M` fragt danach `sectorlength (128 --> 0, 512 --> 1) ?`, nur bei 512 `sectorsequence (1, 2, 3, 4) ?` (Tabellen ab `563CH`: 1 2 3 4 5 6 7 8 / 1 3 5 7 2 4 6 8 / 1 4 7 2 5 8 3 6 / 1 5 2 6 3 7 4 8), dann `ready ?` — **nur `Y` startet**, jede andere Taste kehrt zurück (ohne Meldung!).
* `FORM.B` fragt `DRIVE ?` und `READY?` (ebenfalls `Y`), bei Systemdiskette `ID?`/`INSERT SYSTEMDISK IN DRIVE`.
* `COPY.B`/`COPY.M` bekommen eine **Befehlszeile**: `COPY.M [V] <quelle> TO <ziel>` (Laufwerksziffern 0–3; Vorgabe Quelle 0, Ziel 1; `V` = Vergleich).  Fehler in der Zeile → Fehlercode `44H`.

### 9.2 FORM.M — was es schreibt
* Es formatiert **selbst** (eigene Spurschreiber `54F6` = MFM, `558A` = FM, CTC-Interrupt `54E6`), Spur 76 → 0 absteigend; CRC-Werte sind vorberechnet
  (MFM, 128 B: `62 A7`; FM, 128 B: `5D 30`; ID-Feld-Anfangswerte `30B2`/`21EF`).  Danach **liest** es jede Spur über den Nukleus (`CALL 0BFDH`, Befehl `0AH`, `0D00H` = 26 × 128 bzw. `1000H` = 8 × 512 B) zurück; Bit 6 in `IY+10` = „defective track: nn“ (hex, absteigend).
* **Spur 0 ist immer 26 × 128 B** (E5-Füllung); ab Spur 1 je nach Wahl 26 × 128 oder **8 × 512** (Sektor-ID 1…8, Reihenfolge nach `sectorsequence`).  Ergibt 26 + 76 × 8 = **634 Sektoren** — genau das Format von `M8KBIN`/DISK-Satz.
  Sektor-IDs auf der 128-B-Spur sind 1…26 **in dieser Reihenfolge** (kein ID 126).
* **Spur 0 trägt das Volume-Label (IBM-3740-artig, EBCDIC):** ID 5 = `ERMAP`, ID 7 = `VOL1MUTOS` und ab Offset 71 Felder, **Offset 75 = Sektorlängen-Kennung** (`40` = 128 B, `F2` = „2“ = 512 B; so auch auf `M8KCMD`/`M8KUSR` = `40`).
  Das passt zu §4.6.1 (dort als „VOL1MUTOS“ gefunden).  `FORM.M` erzeugt also genau die Disketten, die §4 beschreibt — **ohne** Zusatzsektor 126 und **ohne** Verschränkung auf Blockebene (die steckt in `mutos_io`, §4.6.3).

### 9.3 Warum FORM.M/FORM.B im Emulator „defekte Spuren“ meldeten
* **Das Formatieren gelingt immer** (`disk verify`: 2002 bzw. 634 Sektoren, 0 CRC-Fehler).  Es scheitert die **Rückleseprüfung**: jede Spur „defective“, bei `FORM.B` `NOT FOR UDOS USEABLE` bzw. `ERROR C6`.
* Ursache (mit Logpoints auf `0955`/`09EC`/`0B3C` und Schreibüberwachung auf `IY+10` belegt): Der Nukleus liest 26 aufeinanderfolgende Sektoren in **einem** Auftrag.  ZVE2 füllt den Puffer, ZVE1 rechnet je Sektor die Daten-CRC **in Software** (`0B93`/`0BB9`, ≈ 160 Takte je Byte ≈ 20 000 Takte je Sektor)
  und vergleicht Zeiger (`[0004H]` von ZVE2) und CRC.  Ist ZVE1 **schneller** als die Platte (FM: 156 Takte je Byte, ≈ 36 000 Takte je Sektor), findet er beim nächsten Sektor den **alten** Zeiger (`JP M,09EC`), bricht die Übertragung ab (`OUT (10H),ADH`) und liest neu.
  Der Wiederholungszähler `[0FCBH]` (16) wird dabei **je Sektor** einmal verbraucht → nach 16 Sektoren Fehler `C6` (`LD D,C6H` bei `09F6`).  Bei MFM (78 Takte je Byte, 8 500 Takte je Sektor) läuft ZVE2 voraus, ZVE1 hinkt hinterher, der Zeiger ist immer frisch.
* **Beleg:** `[0FCAH]` per `e 0x0FCA 0x3E` auf Laufwerk 1 = Typ 3 (MFM) gesetzt → `FORM.M` läuft in 128 **und** 512 Byte (Folge 1) **ohne** „defective track“; mit Typ 2 (FM, Vorgabe) schlägt jede Spur fehl, auf K5601 wie auf MF6400.
* **Was das über echte Hardware sagt, ist offen.**  Der Emulator liefert FM mit 15625 B/s für **alle** Laufwerke (`DriveProfile::bytePeriodCycles`); ein echtes 8″-Laufwerk liefert FM mit 31250 B/s.  Versuch: Rate für `medium_inch == 8` verdoppelt → `FORM.M` am MF6400 lief fehlerfrei durch,
  aber das Booten von einem 8″-Laufwerk A: hing im Boot-ROM (PC 03B4/020D), und `test-format` meldete `bootdisk_mf3200_fmt7` und `bootdisk_mf6400_fmt1` rot.  **Die Änderung ist in dieser Form zurückgenommen**; die verbesserte Fassung (nur FM verdoppelt) steht in §9.11.
* **Für den Anwender:** `FORM.M` auf einem K5601 im Emulator **mit MFM-Typ** benutzen, d. h. vor `FORM.M` `SET DISKCON` auf Typ 3 für das Ziellaufwerk (Poke `[0FCAH]` im Debugger).  Ob das UDOS Ihrer echten Maschine für B:/C: (K5601) ohnehin Typ 3 trägt, ist zu prüfen.

### 9.4 FORM.B (UDOS-/Boot-Format)
* `FORMAT BOOT V 1.0` (`FORMAT V 4.1 1085 MP`): legt vor dem Formatieren **die Systemspuren der Quelldiskette (Laufwerk A:) per Nukleus** (`4264`–`429D`: vier Leseaufträge, darunter `0D00H` = ganze Spur 2) und schreibt sie auf das Ziel; Meldungen `DEFEKTIVE TRACK: nn`, `NOT FOR UDOS USEABLE`, `SYSTEMCOPY NOT POSSIBLE`, `DIRECTORY` (legt das UDOS-Verzeichnis an).
* Im Emulator scheitert es bei FM-Typ **früher** als `FORM.M`: bereits beim Lesen der Systemspuren von A: (`ERROR C6`, derselbe Mechanismus wie §9.3, weil A: bei `[0FCAH] = 2AH` als FM gilt, die Diskette aber MFM ist).
* **Mit MFM-Typ für alle Laufwerke** (`e 0x0FCA 0xFF`) läuft `FORM.B` fehlerfrei durch (`FORM.B`, Laufwerk 1, `Y`): Ergebnis 77 × 26 Sektoren, 0 CRC-Fehler.  Es kopiert die **Systemspuren (Spur 0–2) von A:** auf das Ziel
  (Spur 0: 26 von 26 Sektoren gleich zu A:, Spur 2 ganz gleich; Spur 1 teils E5, weil die Quelle dort selbst Leerbereiche hat) und formatiert den Rest mit `E5`; ein Systemkopf (`SYL`) ist damit auf dem Ziel.
  Das Ziel ist ein UDOS-Format (Verzeichnis `DIRECTORY`), **kein** MUTOS-Volume — dafür ist `FORM.M` da.
* Korrektur zu §9.1: `[0FCAH] = 2AH` bedeutet Laufwerk 0–2 = Typ 2, Laufwerk 3 = Typ 0 (nicht vorhanden), nicht „alle vier Typ 2“; `0xFF` setzt alle vier auf Typ 3.

### 9.5 COPY.M / COPY.B — Plattenkopierer
* Es kopiert **ganze Spuren** (kein Dateikopierer): `COPY.M` liest Spur für Spur ab **Spur 1** bis `last track` (`28H` = 40 bzw. `4DH` = 77) mit Befehl `0AH` aus der Quelle und schreibt mit Befehl `0EH` ins Ziel; mit `V` liest es das Ziel zurück und vergleicht (`verification complete` bzw. `error on track …`, `*** n verification error(s) ***`).
  **Spur 0 wird von `COPY.M` nicht kopiert** — sie entsteht durch `FORM.M` (Label!).
* **Vorbedingung:** `source drive not ready` / `destination drive not ready` / `destination drive write protected` (Fehler `C2`/`C3` des Nukleus); und **die Sektorlänge muss gleich sein**: `COPY.M` liest vorab die Label-Sektoren (Spur 0, ID 7) von Quelle und Ziel und vergleicht **Byte 75**; ungleich → **`sectorlangth is incompatible`** (Schreibfehler im Programmtext).
  Danach setzt es die Spurgröße (`0D00H` bei 128 B, `1000H` bei 512 B).
* **Versuch mit `M8KBIN` als Quelle** (Ziel mit `FORM.M` 512/Folge 1 formatiert): `sectorlangth is incompatible`, weil das Label von `M8KBIN` durch die Bitverschiebung (§4.6.6) `E5` statt `F2` an Offset 75 trägt.  **Bestätigt, dass `M8KBIN`/`M8KROOT` als Abbild beschädigt sind** und nicht kopierbar.
* **Gegenprobe mit intakter Quelle** (eine mit `FORM.M` 512/Folge 1 formatierte Diskette, jeder Sektor ab Spur 1 mit einem Muster beschrieben, als C: gemountet): `COPY.M V 2 TO 1` meldet `verification complete`;
  Vergleich Quelle ↔ Ziel mit `DiskTool`: **608 von 608 Sektoren gleich**, keiner verschieden oder fehlend.  Das Verfahren **FORM.M → COPY.M** funktioniert also im Emulator, sobald das Ziel MFM-Typ hat (§9.3).
* **Reihenfolge der Handgriffe im Debugger** (Beispiel): Ladediskette in A:, leere Diskette in B: **beim Start** (`-b`); `g 80000000`; `keys FORM.M\r`; `e 0x0FCA 0x3E`; Antworten `1`, `1` (512), `1` (Folge), `Y`; `g 300000000`;
  **erst dann** `mount C: quelle.hfe`, `keys COPY.M\sV\s2\sTO\s1\r`, `Y`.  **Eine zweite MUTOS-Diskette schon beim Start gemountet → `DISK INITIALIZATION ERROR C6` (UDOS-Initialisierung, kein MUTOS-Befund, vgl. §2).**

* **`COPY.B`** (UDOS-Format, 26 × 128 B, kein Label-Vergleich): `COPY.B V 0 TO 2` von der Ladediskette (A:) auf ein mit `FORM.B` formatiertes C: (MFM-Typ, `e 0x0FCA 0xFF`) meldet `VERIFICATION COMPLETE`;
  Vergleich: **2002 von 2002 Sektoren gleich** (77 × 26; verglichen wurden Nutzdaten — zum Nachspann s. §9.13).  Damit ist die Kette `FORM.B` → `COPY.B` im Emulator eine funktionierende **Kopie der Ladediskette** (bootfähig, wenn die Systemspuren übernommen sind).

### 9.8 Passen die Sektoren der Ladediskette als FM auf ein MF3200 (8″)?
Rechnung, nicht erprobt: MF3200 = 360 U/min, FM 250 kbit/s = 31 250 B/s → **5 208 B je Spur**.  Die FM-Spur von `FORM.M` (`558A`) belegt je 128-B-Sektor 6 × 00 + FE + 4 ID + 2 CRC (13) + 11 × FF (Lücke 2) + 6 × 00 + FB (7) + 128 + 2 CRC + 26 × FF (Lücke 3) = **187 B**;
26 Sektoren = 4 862 B + Spuranfang (≈ 50 B) ≈ **4 910 B**.  Der UDOS-Zeiger hinter der Daten-CRC (6 B Sektorkontrollblock, §4.6) bringt +156 B = **≈ 5 070 B**: passt, mit ≈ 2,5 % Reserve.
Das entspricht dem IBM-3740-Standard und den vorhandenen 8″-Disketten (`M8KCMD`/`M8KUSR`, 77 × 26 × 128 FM).  **Auf einem 5¼″-K5601 passt FM 26 × 128 nicht** (3 125 B je Spur bei 125 kbit/s): dort ist MFM nötig — das erklärt, warum die Ladediskette MFM ist.
Eine FM-Fassung der Ladediskette müsste sektorweise in eine `.hfe`/`.dmk` mit FM-Spuren umgeschrieben werden (Medium-Ebene: `sector_create` je Spur); ob das Lade-ROM und der Nukleus sie dann lesen (CRC-Konstanten `BF84` statt `E295`, `[0FCAH]` Typ 2), ist ungeprüft.

### 9.10 Boot vom MF3200 (FM), Formatieren und Kopieren auf B:/C: (K5601) — Emulator, 2026-10-23
Aufbau: `--laufwerke MF3200,K5601,K5601,none`, A: = `…_boot_udos_mf3200.hfe` (§9.9), B:/C: K5601.  Nach dem Boot steht `[0FCAH] = 2AH` (alle FM); für die K5601 muss **MFM-Typ** gesetzt werden: `e 0x0FCA 0x3E` (A: Typ 2 FM, B:/C: Typ 3 MFM).
Auf einer echten Maschine gilt dasselbe: FM 26 × 128 passt nicht auf eine 5¼″-Spur (§9.8), der Typ der K5601-Laufwerke muss also MFM sein — woher UDOS ihn dort nimmt, ist offen (§9.7 Nr. 1).

| Handgriff | Ergebnis |
|---|---|
| `FORM.M` Laufwerk 1 (B:), 512 B, Folge 1 | ✅ 634 Sektoren, 0 CRC-Fehler, keine „defective track“ |
| `COPY.M V 2 TO 1` (C: = intakte 512-B-Quelle → B:) | ✅ `verification complete` |
| `FORM.M` 128 B auf B:, danach `COPY.B V 2 TO 1` (C: = MFM-Ladediskette) | ✅ `VERIFICATION COMPLETE`, **2002 von 2002 Sektoren gleich** |
| `FORM.B` Laufwerk 2 (C:) | ❌ `ERROR C6` |

`FORM.B` scheitert, weil es zuerst die Systemspuren von **A:** (FM) mit einem Ganzspur-Auftrag liest — der FM-Ratenmangel des Emulators (§9.3).  Mit MFM-Typ auch für A: und MFM-Ladediskette in A: läuft es fehlerfrei (§9.4).
Wer also eine **bootfähige UDOS-Diskette** in B:/C: braucht, kopiert sie am besten mit `COPY.B` (Ganzspurkopie inkl. Spur 0–2) von einer fertigen Diskette statt `FORM.B` zu benutzen; `FORM.M` + `COPY.M` (512 B) bzw. `FORM.M` + `COPY.B` (128 B) funktionieren vom MF3200 aus.

### 9.11 Korrektur im Emulator: FM-Datenrate am 8″-Laufwerk (2026-10-23)
`DriveProfile::bytePeriodCycles()` verdoppelt die Rate jetzt für **FM an 8″-Laufwerken** (MF3200, MF6400): 31 250 statt 15 625 Byte/s = 78 statt 156 Takte je Byte, wie am echten Gerät (250 kbit/s).  MFM und alle 5¼″-Laufwerke bleiben unverändert.
* Der erste Versuch (§9.3) verdoppelte **auch MFM** am 8″-Laufwerk; das ließ das Boot-ROM hängen (PC 03B4/020D) und färbte `bootdisk_mf3200_fmt7`/`bootdisk_mf6400_fmt1` rot.  **Nur FM** verdoppelt: beide Tests grün, `test-format` 74/74, Standardrunde bis auf einen fremden Fall (s. u.) grün.
* Wirkung: `FORM.M` mit FM-Typ auf einem 8″-Ziel meldet keine „defective track“ mehr (77 × 26 Sektoren, 0 CRC-Fehler).  **`FORM.B` von der MF3200-FM-Bootdiskette (§9.9) auf eine K5601 in B: läuft fehlerfrei durch** (`[0FCAH]=3EH`; Systemspuren übernommen, 2002 Sektoren, 0 CRC-Fehler) — der Handgriff aus §9.10, der vorher mit `ERROR C6` endete.
* **Gelöst (2026-10-23): `FORM.B` mit FM-Ziel am 8″-Laufwerk (früher `ERROR C4`).**  Der Fehler war ein Lagefehler des Lesekopfes im K5122-Modell, kein Zeitproblem (eine Rate von 3/2 statt 2 änderte nichts):
  * Der UDOS-Ganzspur-Schreibauftrag (`0EH`, Anfrageblock `4541`, 26 Sektoren) sucht die Sektoren der Reihe nach (`ZVE2`: ID lesen, Zylinder gegen `[0E9CH]`, Sektor gegen `[0FC9H]` vergleichen, bei Gleichheit schreiben).  Jede **nicht passende ID zählt `[0FCDH]` herunter** (Vorgabe 256); bei 0 meldet ZVE2 Status `44H`, der Nukleus macht daraus `C4` (`0772`/`07C8` setzt nur `C1`/`C2`/`C4`/`C5` beim Eintritt, `0ABF` den ZVE2-Status).
  * Beobachtet (Trace `0A00`–`0B3F`): nach jedem geschriebenen Sektor war die ID des **Folgesektors verpasst**, ZVE2 wartete eine ganze Umdrehung (26 Fehlvergleiche je Sektor).  Nach 10 Sektoren war der Zähler leer — daher „bricht bei Zylinder 2 nach Sektor 10 ab“; Zylinder 0 (3 Sektoren) und 1 (6 Sektoren) kamen noch durch.
  * Ursache: vor dem Schreiben pulst der Treiber MK1 (Steuerwort `91H`, `0AD9`).  Das Modell wertet jeden MK1-Anstieg als Marken-Resync und setzte den Kopf damit auf die DAM vor (Position 18 → 36).  Das Datenfeld (145 Byte inkl. Sync) endete dann **ein Byte vor der nächsten ID** (Kopf 181, FE bei 182); ZVE2 liest danach über `L0A2B`/`L0A1A` zwei Bytes zu viel, verschluckt das FE und fängt erst eine Umdrehung später wieder an.  Am echten Gerät beginnt das Schreiben etwa 12 Byte hinter der ID und endet rund 18 Byte vor der nächsten.
  * Fix (`K5122::beginWriteField`, nur **FM**): der unmittelbar vor `/WE` liegende Resync (höchstens 4 `IN 16H` zuvor) wird zurückgenommen (`resync_prev_pos_`, `resync_ins_` in `k5122.h`).  MFM bleibt unverändert (dort liegt genug Lücke, und das Verhalten ist durch die Bootdisketten-Tests festgenagelt).
  * Wirkung: `FORM.B 1` von der MF3200-FM-Diskette auf ein FM-Ziel (B: MF3200) läuft ohne Fehler durch; alle 26 Sektoren von Zylinder 0 und 2 stimmen mit der Quelle überein.  Zylinder 1 unterscheidet sich in den Sektor-IDs 11, 15 und 17; `FORM.B` überträgt dort nur 6 Sektoren (Auftrag `0300H` Byte) — **nicht weiter geprüft**, ob das so gewollt ist.  (`DiskTool.sector_data` zählt ab 0, nicht nach Sektor-ID.)
  * Tests nach der Änderung: `test-format` 74/74, Standardrunde 4012/4012.
* `cli_mutos8000_boot_rekonstruierte_wurzel` war zeitweise rot (Arbeitskopie der anderen Sitzung, unabhängig von dieser Änderung); in der Standardrunde nach dem FM-Schreib-Fix (4012/4012) grün.

### 9.12 Laufwerksangabe bei FORM.B / FORM.M / COPY.* und Laufwerk A: formatieren (2026-10-23)
* **Die Laufwerksfrage wertet nur die unteren 4 Bit des ERSTEN Zeichens aus** (`FORM.M` `4029: AND 0FH`; `FORM.B` `4029` ebenso).  Am Haltepunkt gemessen: Eingabe `0` → 0 (A:), `1` → 1 (B:), `a`/`A` (0x61/0x41) → **1 = B:**, `b`/`B` → **2 = C:**.
  Wer Buchstaben eingibt, trifft also immer das **nächste** Laufwerk.  **Für A: ist `0` einzugeben**, B: = `1`, C: = `2`, D: = `3`.  `COPY.B`/`COPY.M` nehmen in der Befehlszeile Ziffern (`COPY.M V 2 TO 1`, §9.5).
* **A: formatieren, wenn man von A: gebootet hat:** `FORM.M 0` löscht die Diskette, von der UDOS nachlädt; nur für eine frische Zieldiskette sinnvoll, die Bootdiskette ist danach weg.  Das Programm läuft aus dem Speicher weiter, UDOS braucht danach aber wieder eine bootfähige Diskette in A:.
* **FORM.B mit Einzellaufwerk:** das Programm enthält die Meldungen `ID? + INSERT SYSTEMDISK IN DRIVE …` und `REPLACE FORMATET DISK IN DRIVE …` (Diskettenwechsel im selben Laufwerk).  Ob sich damit die Systemspuren von einer Bootdiskette in A: auf eine zweite Diskette in A: übertragen lassen, ist **nicht erprobt**.
  `COPY.B`/`COPY.M` kennen keine Wechselmeldung; Quelle = Ziel = A: ist ungeprüft.
* **FORM.B mit `0` im Einzellaufwerk — ausprobiert (Emulator, MF3200 FM, Diskettenwechsel im Debugger mit `eject A` / `mount A <abbild> mf3200_26x128`):**
  Reihenfolge der Abfragen: `DRIVE ? 0` → `READY? Y` → **formatiert sofort das Laufwerk, das gerade drin steckt** (die Quelle, wenn man nichts tauscht!) → `INSERT SYSTEMDISK IN DRIVE 0!  READY?` → liest die Systemspuren → `REPLACE FORMATET DISK IN DRIVE 0!  READY?` → schreibt sie.
  Die **leere Zieldiskette muss also vor dem ersten `Y` in A: liegen** (nach dem Start von `FORM.B`, das Programm läuft aus dem Speicher); dann die Bootdiskette zum Lesen, dann wieder die Zieldiskette zum Schreiben.
  Ergebnis im Emulator: Formatieren (77 × 26 Sektoren, 0 CRC-Fehler) und Lesen der Systemspuren laufen; das **Schreiben der Systemspuren endete anfangs mit `ERROR C4`** — der FM-Schreibfehler aus §9.11, seit dem Fix dort gelöst ; der Einzellaufwerk-Ablauf mit Diskettenwechsel läuft danach ohne Fehler durch (`disk verify A`: 77 Spuren, 2002 Sektoren, 0 CRC-Fehler).  Auf echter Hardware ist der Ablauf damit der Weg, die Systemspuren zu übertragen; die Dateien (`COPY.B` braucht zwei Laufwerke) kämen dann nicht mit — vollständig bleibt die Abbildkopie.
* **Praktische Kopie der Bootdiskette mit einem MF3200:** das Abbild `…_boot_udos_mf3200.hfe` (§9.9) mit dem Greaseweazle auf eine zweite Diskette schreiben.

### 9.13 Bootdisketten bauen: Verfahren, Laufwerkstypen, K5601 (2026-10-24)

**Kernbefund: der Laufwerkstyp steht in der Diskette, nicht in der Hardware.**  Die UDOS-Initialisierung der Ladediskette (Speicher `1040H`–`107BH`, geladen von **Zylinder 2, Sektor-ID 1, Offset 120/121**) fragt nur ab, *welche* Laufwerke antworten, und setzt dann
`LD A,2AH / AND D / LD (0FCAH),A` — die **Konstante `2AH`** (Zeile 1078H, Byte `2A` an Offset 121 des Sektors) ist der Typ je Laufwerk, UND-verknüpft mit der Anwesenheitsmaske `D`.  Die Zuordnung steht in §9.1: 2 Bit je Laufwerk, Laufwerk 0 in den unteren Bits, `1` = 40 Spuren MFM, `2` = 77 Spuren **FM**, `3` = 77 Spuren **MFM**.
Dieselbe Tabelle benutzen `FORM.B`, `FORM.M`, `COPY.*` **und** `mutos_io` (der Kernel-Plattentreiber ruft den Nukleus-Treiber, §4.1) — es gibt in den Programmen keine zweite Einstellung.  Ob eine Bootdiskette „zu den Laufwerken passt", entscheidet also allein dieses eine Byte plus das Aufzeichnungsverfahren der Spuren.

| Laufwerke A: / B: / C: (/ D:) | Spuraufzeichnung | Konstante | Befund |
|---|---|---|---|
| alle 8″ FM (MF3200) — Auslieferung | FM | `2AH` (unverändert) | ✅ |
| A: MF3200 (FM), B:–D: K5601 (MFM) — Maschine des Anwenders | A: FM, Wurzel/Daten MFM | `FEH` (bis 2026-10-24 `3EH`) | ✅ |
| A:–D: K5601 (5¼″ MFM) | MFM | `FFH` (bis 2026-10-24 `3FH`) | ✅ |
| 40-Spur-Laufwerke K5600.10 | MFM, 40 Zylinder | `1`-Paare (z. B. `15H`) | nicht erprobt (`FORM.*` kennt `28H` Spuren) |
| 8″ MFM (MF6400) | MFM | `FFH` | nicht erprobt; der Emulator liefert MFM am 8″-Laufwerk weiter mit 250 kbit/s (§9.11) |

**Vier Laufwerke, AND-Maske (2026-10-24).**  Die Anwesenheitsmaske `D` wirkt nur als UND: ein Laufwerk, das nicht antwortet, bekommt Typ 0, auch wenn die Konstante ihm einen Typ zuweist.  Die Konstante darf deshalb **mehr** Laufwerke belegen, als vorhanden sind.  Die K5601-Ladedisketten tragen daher `FFH` (A:–D: MFM) und `FEH` (A: FM, B:–D: MFM) statt `3FH`/`3EH`; `2AH` (A:–C: FM) bleibt.  Vorher hatte D: (rk3) Typ 0 und `/etc/mount /dev/rk3` scheiterte mit `err on dev 4/3 er=0,302` (§10.1).
**Gegenprobe (gemessen 2026-10-24):** `FFH` an **drei** K5601 (`--laufwerke K5601,K5601,K5601`) und an **vier**: der Lader-Bildschirm ist in beiden Fällen gleich (Menü, `floppy - drive 0 1 2 3`, `change / ready (r)`), danach `mem = 196608`, `single user login:`; keine Meldung `ERROR`/`C2`/`C6`, kein `err on dev` (Wächter `mutos8000_boot_ladediskette_k5601`, drei Laufwerke).  Vier K5601 mit der Wurzel in C: und `cmd_mfm` in D: (nach dem Login): `mount /dev/rk3 /mnt`, `ls /mnt/bin`, `umount`, erneut `mount` ohne Eingriff im Debugger (Wächter `mutos8000_datendisketten_k5601_vier`).  `FEH` mit `MF3200,K5601,K5601,K5601`: `mount /dev/rk3`, `ls /mnt/bin` ebenso (ad hoc).

Die Konstante bestimmt, was `FORM.*` aufzeichnet (Typ 3 → MFM-Schreiber `54F6`, CRC-Anfangswert `E295`; Typ 2 → FM-Schreiber `558A`, `BF84`) und was der Treiber als Datenrate/CRC beim Lesen annimmt.  **Programme müssen nicht geändert werden**; nur diese Konstante.

**Verfahren A — im Gast kopieren (kein Werkzeug außerhalb nötig).**  Zwei Laufwerke, Quelle in A:, leere Diskette in B: (**erst nach dem Start einlegen/mounten**, sonst `DISK INITIALIZATION ERROR C6`, §2):
`FORM.B` → Laufwerk `1` → `Y` (formatiert alle 77 Spuren, kopiert die Systemspuren 0–2) → `COPY.B V 0 TO 1` → `Y` (kopiert alle Spuren und vergleicht).  Gemessen mit der Ladediskette `…_boot_udos_k5601.hfe` (`3FH`) an drei K5601: `VERIFICATION COMPLETE`; **Nutzdaten und 4-Byte-Sektorkontrollblock aller 2002 Sektoren gleich** (die Füllbytes dahinter nicht: UDOS schreibt 6 statt der 8 Nachspannbytes, die das DiskTool anlegt — folgenlos), `check --full` ohne Befund, die Kopie bootet bis zum Lader-Menü (`[0FCAH] = 3FH` damals; seit 2026-10-24 `FFH`).
`FORM.B` formatiert nach dem Typ, den das **laufende** System für das Ziellaufwerk führt (`[0FCAH]`), und `COPY.B` überträgt die Konstante der Quelle mit; für eine K5601 als Ziel muss die gebootete Diskette also schon `FFH`/`FEH` (bzw. `2AH`) tragen (oder `[0FCAH]` vor `FORM.B` im Debugger gesetzt sein), sonst formatiert `FORM.B` im falschen Verfahren.  Mit nur **einem** Laufwerk überträgt `FORM.B 0` nur die Systemspuren (§9.12); die Dateien (Lader-Menü, `FORM.*`, `COPY.*`, Skripte, `mutos_1216`, `mutos_io`) kommen nur mit `COPY.B`.

**Verfahren B — offline mit dem DiskTool** (so sind die Disketten unten entstanden): leere Diskette im Ziel-Profil anlegen, **alle 2002 Sektoren samt Nachspann** aus einer vorhandenen Ladediskette übertragen, Konstante patchen.  Die Dateikette von UDOS liegt im Nachspann (§4.6), deshalb ohne `sector_write_tail` bootet es nicht:

```python
from app.core_binding.k1520disk import DiskTool       # sector_*: Sektor-INDEX ab 0, nicht Sektor-ID
quelle = DiskTool.open_raw("a5120_mutos8000_boot_udos_mf3200.hfe")
ziel   = DiskTool.open_raw("neu.hfe", read_only=False)   # vorher: k1520disktool create neu.hfe --fs udos_ss77   (MFM, 5¼″)
                                                         #        oder  --fs mutos8k_fm                        (FM, 8″)
for c in range(77):
    for i in range(26):
        ziel.sector_write(c, 0, i, quelle.sector_data(c, 0, i))
        ziel.sector_write_tail(c, 0, i, quelle.sector_tail(c, 0, i))
s = bytearray(ziel.sector_data(2, 0, 0))                 # Zylinder 2, Sektor-ID 1
assert s[120:122] == bytes([0x3E, 0x2A])                 # LD A,2AH
s[121] = 0xFF                                            # FFH alle MFM · FEH A: FM, B:-D: MFM · 2AH A:-C: FM
ziel.sector_write(2, 0, 0, bytes(s)); ziel.flush(); ziel.close()
```

Dann `k1520disktool check --full --fs udos_ss77 neu.hfe` (soll „ohne Befund" melden) und ein Bootversuch.  Als Container `.hfe` verwenden — der DMK-Schreiber macht bei FM falsche CRCs (§9.9).

**Was beim Wechsel des Verfahrens zu beachten ist**
* **FM passt nicht auf 5¼″** (§9.8): auf der K5601 muss alles MFM sein, auf dem MF3200 alles FM.  Eine Diskette mit dem falschen Verfahren lehnt der Kern ab (`Diskette ist MFM-aufgezeichnet, Laufwerk 'MF3200' beherrscht das nicht`).
* **Quelle und Konstante zusammen ändern.**  Eine MFM-Wurzel an einem Laufwerk mit Typ 2 bootet **nicht**: mit der unveränderten Ladediskette (`2AH`) und der MFM-Wurzel in C: erscheint nur `mem = 196608`, kein `single user login` (gemessen).
* **Die Wurzeldiskette muss zum Typ des Laufwerks passen.**  `a5120_mutos8000_root_fm.hfe` ist FM; für ein MFM-Laufwerk gibt es sie als MFM-Fassung (unten).  Die Blockabbildung (Verschränkung 2, Spurversatz 6, §4.6.3) hängt nur an den Sektornummern, nicht am Verfahren — es genügt, die 2002 Sektoren in eine MFM-Diskette zu übertragen (`udos_ss77` als Träger; ein eigenes `mutos8k_mfm`-Profil gibt es im Katalog noch nicht, die Erkennung führt die Diskette deshalb als `udos_ss77`).
* **Das 5¼″-Laufwerk ist 80-Spur-fähig**, die Ladediskette nutzt 77 Zylinder; der Altbestand auf 77–79 (§9.0) wird für eine neue Diskette nicht übernommen.  Beim Aufbau eines MFM-Mediums mit `udos_ss77` entstehen genau 77 Zylinder.
* **Die Ziellaufwerke dürfen beim Start nicht mit einer zweiten Diskette bestückt sein** (§2), und `[0FCAH]` kann zur Not im Debugger gesetzt werden (`e 0x0FCA 0x3F`), ohne die Diskette zu ändern — nützlich zum Ausprobieren, nicht als Dauerlösung.
* **Echte Hardware:** nichts davon ist an einem echten A5120.16 erprobt.  Offen bleibt, ob das UDOS der Original-Maschine dort denselben Initialisierungspfad (`2AH`) hatte oder ob die Konstante in der Praxis über die Laufwerksbestückung gesetzt wurde.

**Was für eine vollständig funktionstüchtige K5601-Bootdiskette zu ändern ist — Antwort auf die Frage:**
1. **Betriebssystemkonfiguration: ja, ein Byte** — `2AH` → `FFH` (A:–D: MFM; ursprünglich `3FH`, drei Laufwerke) bzw. `FEH` (A: bleibt FM, B:–D: MFM; ursprünglich `3EH`), Zylinder 2, Sektor-ID 1, Offset 121.  Ohne diese Änderung liest und formatiert UDOS die Laufwerke als FM: `FORM.B`/`FORM.M` melden an einer K5601 „defective track“/`C6` (§9.3), und `mutos_io` kann eine MFM-Wurzel nicht lesen.
2. **Programme: nein.**  `FORM.B`, `FORM.M`, `COPY.B`, `COPY.M`, der Lader, `mutos_1216` und `mutos_io` lesen den Typ aus `[0FCAH]`; sie liefen mit `3FH`/`3EH` unverändert (Formatieren, Kopieren, Boot bis `login`).
3. **Spuren und Sektoren: MFM, 26 × 128 B, 77 Zylinder, Sektor-IDs 1…26 in Reihenfolge, Nachspann übernehmen** (Verfahren B) oder mit `FORM.B`/`COPY.B` im Gast erzeugen (Verfahren A).
4. **Wurzel und Datendisketten in MFM** (`FORM.M`-Disketten sind es ohnehin; die M8K-Wurzel muss einmal in MFM übertragen werden, s. u.).

**Vorhandene, getestete Disketten** (Original `…_boot_udos.dmk` in `disks/a5120_mutos8000/`, die gebauten in `disks/a5120_16_MUTOS/`, Neubau aller fünf: `tools/mutos8000/bau_alle.py`; alle im Emulator, nichts auf echter Hardware):

| Datei | Zweck | Aufzeichnung / Konstante | Getestet |

## 10. Datendisketten: Einbinden, Best-of-Satz, Bau (2026-10-24, #22)

### 10.1 Wie MUTOS Datendisketten einbindet (im Emulator ausprobiert)

* **Geräte:** `/dev/rk0`…`rk3` = `brw 4,0..3` = Laufwerk **A:…D:** (die Maske von `mutos_io` zeigt `floppy - drive 0 1 2 3` ↔ `mutos - rk 0 1 2 3`).  Die Wurzel liegt in `rk2` = C:.  Nach dem
  Tausch der Ladediskette gegen die Wurzel ist **A: frei** (die Ladediskette wird nicht mehr gebraucht), dazu B: — **bei drei Laufwerken sind also A: und B: für Daten frei**, C: trägt die Wurzel.
* **Mounten** (angemeldet als `root`): Diskette einlegen, dann `/etc/mount /dev/rkN /punkt` (die Wurzel hat `/mnt`, `/usr`, `/tmp`); `/etc/umount /dev/rkN` vor dem Herausnehmen.  Es gibt **keinen Neustart**
  und keinen Wechselbefehl: gemountet wird zur Laufzeit.  `.profile` setzt `PATH=:/mnt/bin:/usr/bin:/bin:/etc:/mnt/etc:/tmp/bin:/mnt:/usr:/tmp` — damit sind die Rollen `cmd`→`/mnt`,
  `usr`→`/usr`, `bin`→`/tmp` ohne Eingriff in die Wurzel benutzbar (Befehle werden ohne Pfad gefunden).  **`/etc/mtab` wird von diesem `mount` nicht geführt**, `cat /etc/mtab` zeigt nur Reste.
* **Im Emulator** (`k1520dbg`): `mount A <abbild> udos_ss77` (ohne vorheriges `eject`; geht erst NACH der Anmeldung — vor `BOOT MUTOS` eingelegt → `C6`, §2).  **Das Format heisst `udos_ss77`** auch für FM-Disketten
  und `.td0`; **`mutos8k_fm`/`mutos8k_mfm` sind Dateisystemprofile des DiskTools, kein Mount-Format** — der Mount wird mit „Unbekanntes Format“ abgelehnt, das Laufwerk bleibt leer, und der Kernel antwortet
  mit `err on dev 4/N  bn=1 er=0,302` (viermal), `mount: I/O error`.  Das war die Ursache der bisher offenen rk3-Meldung von §3a (zugleich: dort war die Diskette nie eingelegt).
* **Die Aufzeichnung muss zum Laufwerk passen** (wie bei der Wurzel, §9.13): MF3200 nimmt nur FM, K5601 nur MFM; die Disketten gibt es deshalb in beiden Fassungen.  Eine Altbestandsdiskette mit 83 Spuren (DISK-CMD)
  wird im K5601 abgewiesen („83 Spuren mit Daten, Laufwerk 'K5601' erreicht nur 80“).
* **Welche Geometrie liest `mutos_io`?  Nur 26 × 128 B** (Interleave 2, Spurversatz 6, §4.6.3).  Ausprobiert mit `a5120_mutos8000_cc1.td0` (8 × 512, DISK-Satz) in B: an K5601: `err on dev 4/1 bn=1 er=0,304`
  (Sektor 9 auf einer 8-Sektor-Spur nicht gefunden, §4.2), `mount: I/O error`.  **Der DISK-Satz und `M8KBIN` (8 × 512) sind mit dem Lader dieser Ladediskette nicht einbindbar** — die offene Frage aus §4.1/§9.6 ist damit
  beantwortet (nein).  Ihr Inhalt wird deshalb auf 26 × 128 verteilt (§10.3).  **`M8KCMD`/`M8KUSR` (FM, 26 × 128) lassen sich dagegen direkt als `.td0` mounten** (`mount B …m8k_cmd.td0 udos_ss77` an MF3200), `ls -l /mnt/bin` listet alle
  Dateien; unlesbare Blöcke (§4.7.5) bleiben unlesbar.  Eine `.td0` wird nicht zurückgeschrieben.
* **Laufwerksgrenze: D: (rk3) braucht einen Eintrag in `[0FCAH]`.**  Die Laufwerkstyp-Konstante belegt je Laufwerk 2 Bit; `2AH` (MF3200-Ladediskette) belegt nur A:–C:, D: hat Typ 0 =
  „nicht vorhanden“, der UDOS-Nukleus antwortet mit `C2` („nicht bereit“), `mutos_io` meldet `err on dev 4/3 er=0,302`.  **Seit 2026-10-24 gilt das nur noch für `mf3200`**: die K5601-Ladedisketten tragen `FFH`/`FEH` (§9.13, AND-Maske), D: mountet ohne Eingriff
  (Wächter `mutos8000_datendisketten_k5601_vier`).  Bei `mf3200` bleibt der Handgriff: im Debugger `e 0x0FCA 0xAA` (vier Laufwerke FM) **vor** dem `mount`, danach `/etc/mount /dev/rk3 /mnt` fehlerfrei (Wächter `mutos8000_datendisketten_mf3200_d`);
  dauerhaft wäre es das Byte an Zylinder 2, Sektor-ID 1, Offset 121 der Ladediskette (`bau_ladediskette.py` kennt dafür keine Vier-Laufwerke-FM-Variante; nicht gebaut).
* **Programme:** was auf den Disketten steht, läuft auf dem Kernel der Ladediskette (`ls`, `wc`, `ps`, `who`, `size`, `passwd`, `mkfs`-Aufruf, `cc` samt `c0`/`c1`/`c2`/`as`/`ld` — ein C-Programm
  `main(){write(1,"hi\n",3);}` wird übersetzt (`cc -o /tmp/h /tmp/h.c`) und läuft), **mit einer Ausnahme: die `pwd` des DISK-Satzes (1987, gleiche Größe wie die von `M8KCMD`) gibt `/` aus und kehrt dann nie zur Shell zurück**
  (die 1986er läuft).  Deshalb steht auf `cmd` die M8KCMD-`pwd`.  Die Wurzel (46 KB frei) genügt dem Übersetzer für die Zwischendateien in `/tmp`.

### 10.2 Handgriffe für den Anwender (Schritt für Schritt)

Drei K5601 (MFM; bei MF3200 die Disketten ohne `_mfm`; bei gemischter Maschine MF3200 + 2 × K5601 trägt A: FM, B:/C: MFM):

1. Ladediskette in A:, `BOOT MUTOS` (§2), **nach der Aufforderung** Ladediskette heraus, Wurzel `…_root_mfm.hfe` nach C:, `r`, Anmeldung `root`.
2. A: ist frei ⇒ `…_usr_mfm.hfe` in A:, `…_cmd_mfm.hfe` in B:.
3. `/etc/mount /dev/rk0 /usr` und `/etc/mount /dev/rk1 /mnt`.  Danach `ls /mnt/bin`, `ls /usr/lib`, Befehle ohne Pfad.
4. C-Programm: Datei mit `echo '…' > /tmp/x.c` oder `ed` anlegen, `cc -o /tmp/x /tmp/x.c`, `/tmp/x`.
5. Wechseln: `/etc/umount /dev/rk0`, Diskette tauschen (z. B. `…_bin_mfm.hfe`), `/etc/mount /dev/rk0 /tmp` — dann stehen `adb`, `mt`, `tar` im PATH (`/tmp` hat dort 195 KB frei).
6. Vor dem Auswerfen **`/etc/umount`** der Datendisketten (sie sind schreibbar gemountet) und `sync`.

### 11.1 Der Plattenweg vom Kernel bis zum Controller (gemessen/abgeleitet)

```
Kernel rkstrategy (6B06)  ->  Mailbox D532 (Minor, Lesen/Schreiben, Puffer, Zähler, Blocknummer)  ->  mutos_io 90EB..9160
  IX = Mailbox:  IX+7 Minor, IX+8&7F = 1 -> Schreiben, IX+2/3 Puffer, IX+14/15 Zähler, IX+18/19 Blocknummer (hoch/niedrig)
  Minor -> Laufwerk:  Tabelle A12A[4]  (rk -> Laufwerk, aus der Maske, 11.4)          IY = A55A (Auftrag), IY+0 Laufwerk, IY+1 0BH Lesen / 0FH Schreiben
  sub_9800: Block -> (Zylinder, Sektor), Auftragsblock 996E, Aufruf des UDOS-Nukleus  CALL 0BFDH -> JP 0700H
```

Auftragsblock des Nukleus (`IY = 996EH`), Feldbedeutung aus dem Nukleus (0700–0770) gelesen: +0/+1 Befehl (`0BH` Lesen, `0FH` Schreiben, Bit 0 = asynchron mit Rückruf),
+2/+3 Puffer, +4/+5 Länge in Byte (nur Bit 7 von +4 zählt), +6/+7 Rückruf „fertig“ (`9893H`), +8/+9 Rückruf „Fehler“ (`9893H`), +10 Status (`C1`…`C6`, `44H`/`45H` aus ZVE2),
**+11 = (Laufwerk << 5) | (Sektor-ID − 1)**, **+12 = Zylinder**.  Der Nukleus rechnet Sektor-ID = (+11 & 1FH) + 1 und lehnt ID > 26 mit `C4` ab (`0770`).

### 11.2 A) Geometrie 8 × 512 (DISK-Satz lauffähig machen)

**mutos_io: die Umrechnung `%9840–%9966`, kommentiert** (gemessen: jede Stelle mit dem Verhalten aus §4.6.3 abgeglichen, danach gepatcht):

```
9800 sub_9800   (997E)=IY  Puffer (9970)=IY+2/3  Rest (997C)=(IY+4 & 80)|IY+5<<8 (<= 1000H)  IY+4/5:=0 (Zähler "übertragen")
982A (9972)=0080          Länge je Nukleus-Aufruf = EIN 128-B-Sektor;  (9974)=(9976)=9893 Rückruf
983F (996E)=IY+0/IY+1|01  Befehl;   9843: (9979)=L ror 3 = Laufwerk<<5
984A HL = bn (IY+11/12)   9850: HL = 4*bn   (logischer 128-B-Sektor l)
9852..9863  8× Schiebe-Subtraktion mit DE=0D00H (= 26<<7):  L = l div 26 -> (996C)=rel,  H = l mod 26 -> (996D)=pos
986D..9873  (996B) = 6*rel mod 26                                       <- Spurversatz 6
993F sub_993F x = 2*pos;  if x >= 26: x++;  x = (x + (996B)) mod 26      <- Verschränkung 2 (erst 13 ungerade, dann 13 gerade)
            C = x (= Sektor-ID−1);  B = rel+1 (Zylinder 0 ist nicht Teil des Blockraums);  (9979)=(9979&E0)|C;  (997A)=B
991B sub_991B nächster 128-B-Sektor: pos++;  bei 26: pos=0, rel++, (996B) = (996B+6) mod 26
9893 Rückruf je fertigem Nukleus-Aufruf (DI): IY+4/5 += 0080;  Rest -= 0080;  Rest = 0 -> Ende (98ED);  sonst Puffer += 0080, 991B, 993F, CALL 0BFDH
```

Ein 512-B-Kernelblock sind also **vier** Nukleus-Aufrufe zu je 128 B, jeder mit eigener Sektorsuche; die Daten werden vom Nukleus direkt in den Puffer `IY+2/3`
des U880-Speichers gelesen (INIR/OTIR der ZVE2, `0A8E`/`0AF7`), die Übertragung zum EM geschieht im Rückruf von `mutos_io` (ab `9163`, abgeleitet), nicht in der Umrechnung.

**UDOS-Nukleus (gemessen): er kann 512-B-Sektoren, die Länge steht aber nicht im Auftrag, sondern global in `[0003H]`.**  Das Feld „N“ der Sektorkennung liest er
**nicht** (`0A46`: `IN A,(16H)` ohne Vergleich).  `[0003H] & 0FH` = Sektorlänge / 128 (`0739`–`0744` teilt die Länge durch diese Zahl, `0A56`/`0B9D` laufen so
oft 128 Byte); `FORM.M` schreibt `01` für 128 B und `04` für 512 B (`40B5`–`40CE`, `4229`; die Länge 1000H je Spur), danach wieder `01`.  Die Aussage in CLAUDE.md
(„Nukleus-Treiber `0794: AND 0FH` patcht die Sektorgröße in `0AAE`/`0AB7`“) gilt für **UDOS 4.3 des A5120**, **nicht** für diesen Nukleus (`0794` ist hier die
Laufwerkstyp-Auswertung).  `mutos_io` setzt `[0003H]` genau einmal, in der Initialisierung `%919A` (`LD A,(0003H) / OR 01H / LD (0003H),A`), **nach** der Maske —
ein Poke vor dem `r` der Maske wird zu `05` (4 | 1 = 5 × 128 B) und endet mit `er=0,306` (`C6`, Datenfeld-CRC); gemessen.

**Kernel (abgeleitet):** keine Geometrie im Kernel außer **einer Grenze** in `rkstrategy`: Blocknummer ≥ `0260H` = **608** (= 76 Zylinder × 8) → Fehler (`6B14–6B1A`, Wort bei Offset 0x6B16).
Das ist genau der Blockraum der 8×512-Disketten (Zyl. 1–76); die 26×128-Disketten haben nur 494 Blöcke.  Das spricht dafür, dass der Kernel für 8×512 gebaut ist
(Abgeleitet, kein Beweis).  Eine Tabelle „Blöcke je Gerät“ gibt es nicht.

**Patchliste `mutos_io` für 8 × 512** (Datei `dateien/mutos_io`; gemessen als Speicherpoke und als Dateipatch bis zur Anmeldung):

| Adresse | Offset | alt | neu | Zweck |
|--|--|--|--|--|

| `9850`–`9880` (49 B) | 0x750 | `29 29 06 08 11 00 0D AF ED 52 …` | `7D E6 07 32 6D 99 CB 3C CB 1D CB 3C CB 1D CB 3C CB 1D 7D 32 6C 99 AF 32 6B 99` + 23×`00` | pos = bn & 7, rel = bn >> 3 |

Danach ist Block *n* = Zylinder 1 + *n*/8, Sektor-ID *n* mod 8 + 1 — die lineare Folge des DISK-Satzes (§4.2).

**Messung.**  (a) Speicherpoke nach `BOOT MUTOS` an der Maske (`k1520dbg`, Skript im Verzeichnis `versuche/`), DISK-ROOT (`…_root.td0`) als Wurzel in C:, Laufwerke K5601 ×3:
`single user login: root`, `ls -l /` listet `bin dev etc mnt tmp usr` (Jun 27 1986 / Mar 17); (b) `…_cc1.td0` in B:, `/bin/mount /dev/rk1 /usr`, `ls /usr/bin` und `cat /usr/include/ctype.h` lesen richtig;
(c) **Schreiben:** `…_cc2.td0` in B:, `echo hello > /usr/t`, `sync`, `umount`, `mount`, `cat /usr/t` → `hello` (Zurücklesen nach `umount` geht über die Platte); (d) **Dateiweg ohne Poke**:
`mutos_patch.py io-8x512` und `zdos-einheit0` (11.6) auf die Archivdateien, `bau_ladediskette.py … --laufwerke k5601`, dann B: = CC1 und C: = ROOT **schon beim Start** eingelegt: Anmeldung, `ls -l /`, `mount /dev/rk1 /usr`, `ls -l /usr/bin` (`as c_beispiel.c cc ed ld`).
Ein Lauf bis zur Anmeldung dauert ≈ 1 min Rechenzeit.

**Grenzen und Risiko (abgeleitet).**  (1) **Entweder–oder:** mit dem Patch liest `mutos_io` nur noch 8×512; die 26×128-Disketten (M8K-Satz, rekonstruierte Wurzel, Best-of-Satz) gehen dann nicht.
Ein Umschalten je Diskette wäre möglich (Etikett Zyl. 0, ID 7, Offset 75: `40` = 128 B, `F2` = 512 B, §9.2), ist aber nicht gebaut — **offen**; sauberer sind zwei Ladedisketten-Varianten.
(2) Der Auftragszähler muss ein **Vielfaches von 512** sein, sonst trifft `Rest = 0` nie (Endlosschleife in `9893`); der Kernel schickt Blöcke (512 / 1024 B), Swap-Aufträge sind Vielfache von 256 B — **Swap-Zähler mit 256 B wären ein Fehler**, im Lauf nicht beobachtet.
(3) Jeder Auftrag liest **einen** Sektor, die nächste ID kommt oft schon vorbei: der DISK-Satz ist linear (IDs 1…8) → u. U. eine Umdrehung je Block (langsam, aber lauffähig); Verbesserung (Zähler bis Spurende in einem Aufruf, Nukleus liest aufeinanderfolgende IDs) **nicht versucht**.
(4) **Die Wurzel muss `s_fsize` ≤ `swplo` einhalten** (11.5): DISK-ROOT hat 352, `swplo` ist 250 — Überschneidung, im Kurzversuch nicht ausgelöst (kein Swap).
(5) Der Kernel-Block 0 ist Zyl. 1 auf beiden Sätzen; Zylinder 0 (26×128) wird nie angefasst — gilt unverändert.

### 11.3 B) Anzahl der Laufwerke

Vier, an vier Stellen (alle gemessen oder aus dem Disassemblat):

| Stelle | Wert | Befund |
|--|--|--|
| K5122 / 8212 (Port 18H, hohes Nibble = /SE) | 4 Auswahlleitungen | Hardware: mehr als 4 Laufwerke kann die K5122 nicht |
| Anwesenheitsprüfung Zyl. 2, ID 1, Offset 0–120 (`1046`–`1078`) | 4 Durchläufe (`LD DE,0004H`), Bit 7 von Port 12H | **gemessen**: nur „antwortet das Laufwerk“, kein Lesen der Diskette |
| `[0FCAH]` (Zyl. 2, ID 1, **Offset 121**) | 2 Bit je Laufwerk, `AND` mit der Anwesenheitsmaske: heute `FFH`/`FEH`/`2AH` | §9.13; Typ 0 ⇒ `C2` |
| Nukleus `0785`: `CP 04H` / `JR NC` → `C2` | Laufwerksnummer ≥ 4 abgewiesen | **gemessen** (11.7) |
| mutos_io: Maske `floppy - drive 0 1 2 3` / `mutos - rk 0 1 2 3`, Tabelle `A12A[4]` | 4 Einträge | **gemessen**, indiziert **ungeprüft** mit dem Minor (`9111`: `A12AH + IX+7`) |
| Kernel `rkopen` (`6ADA`): `CP minor,#4`, sonst `u_error = 6` (ENXIO) | 4 Minors | abgeleitet (Wort bei 0x6AF0, Wert 4 im Byte 0x6AF1); `rkstrategy` prüft den Minor nicht |
| `/dev` | `rk0`–`rk3` = `brw 4,0..3`, `rrk0`–`rrk3` = `crw 13,0..3` | gemessen (§4.7.2); `rk4`… gibt es nicht |

**Zuordnung `floppy ↔ rk` ist einstellbar und interaktiv (gemessen).**  Die Maske fragt je **Spalte „floppy – drive“ i** die **rk-Nummer** (Ziffer 0–3; `Enter` behält den gezeigten Wert, `x` setzt zurück, `r`
beendet — **nur am Anfang einer Runde**, nach dem 4. Wert beginnt eine neue; doppelte Nummer → `rk - duplikate`; Ziffer außerhalb → `number (0...3)`; sonst `not assign rk`).  Beim Beenden entsteht
`A12A[rk] = Laufwerk` (`A1F1–A20F`); `A126[]` wird bei jedem Maskenaufbau auf `0 1 2 3` zurückgesetzt (`A13A–A143`), ein Vorbelegen der Tabelle im Abbild genügt also **nicht**.

### 11.4 C) Wurzel in A: statt C: (rk2)

**Ohne jeden Patch möglich (gemessen).**  Ladediskette in A:, `BOOT MUTOS`, an der Maske die Ladediskette gegen die Wurzel **in A:** tauschen (`eject A`, `mount A …_root_mfm.hfe`) und
`2` `1` `0` `3` tippen (Laufwerk 0 → rk2, 1 → rk1, 2 → rk0, 3 → rk3), dann `r`.  Bildschirm: `mutos - rk.........:   2   1   0   3`, `mem = 196608`, `single user login: root`, `ls -l /` wie sonst;
`A126` danach `02 01 00 03`.  Skript `versuche/wurzel_in_a_maske.dbg`.  Der Kernel liest weiter von rk2 — `mutos_io` biegt rk2 auf das physische Laufwerk 0.  Der Meldetext `…root - disk on rk2` bleibt dabei stehen (Text, kein Ablauf).

**Ladediskette im Weg?**  Nein (gemessen): die Disketten werden nach dem Laden nicht mehr gebraucht — Nukleus (0000–0BFF) und `mutos_io` liegen im Speicher.  Mit dem Patch aus 11.6 bootet MUTOS, **während die Ladediskette in A: bleibt** und die Wurzel in C: liegt;
das „remove … boot - disk“ ist nur Text.

**Dauerhaft in A: (Kernelpatch, gemessen als Speicherpoke).**  `rootdev`, `swapdev` und `pipedev` sind drei aufeinanderfolgende Wörter `0402` (Major 4 = Floppy, Minor 2) im Datenbereich des Kernels:

| Wort | Adresse (= Offset in `mutos_1216`) | heute | neu für A: |
|--|--|--|--|
| `rootdev` | `887C` (Minor-Byte `887D`) | `04 02` | `04 00` |
| `swapdev` | `887E` (`887F`) | `04 02` | `04 00` (oder 11.5) |
| `pipedev` | `8880` (`8881`) | `04 02` | `04 00` |

Belegt durch die Verwendung: `iinit` (`0746`–`0764`) holt `bdevsw[rootdev >> 8]` ab `8766` (8 Byte je Eintrag: open, close, strategy, tab; Major 4 = `6ADA 6AFE 6B06 8E82`) und liest Block 1 von `rootdev`;
die Swap-Funktion (`5E50`, `5E98`) benutzt `887E`, die Rohr-Zuteilung (`39E8`) `8880`.  **Ändert man `rootdev`, muss `pipedev` mit** (sonst werden Rohr-Inodes auf einem nicht eingehängten Gerät angelegt — abgeleitet).
Gemessen: mit `e em:887D 00`, `e em:887F 00`, `e em:8881 00` (EM-Speicher ist ab `em:0` der flache Kernel), Wurzel in A:, Standardzuordnung `0 1 2 3`: Anmeldung und `ls -l /` wie sonst (`versuche/kernel_root_rk0.dbg`).
Zusätzlich anzupassen, wenn man es sauber haben will: der Meldetext `on rk2` in `mutos_io` (Adresse `A0C9`, Offset 0xFC9, `32` → `30`).  Auf der Wurzel selbst ist **nichts** zu ändern: `/dev/rk0`–`rk3` bleiben, `/etc/mtab`, `rc` gibt es nicht; `/dev/swap` ist auf `M8KROOT` 4,2, auf DISK-ROOT 4,0 (§4.7.6) — **nur für `ps`/`pstat`/`adb`**, der Kernel liest den Knoten nicht.
Die DISK-ROOT-Konvention (`/dev/swap` = 4,0) lässt vermuten, dass die spätere Fassung mit Wurzel/Swap an `rk0` eingerichtet war (**Vermutung**).

### 11.5 D) Swap-Bereich

**Lage (abgeleitet aus dem Disassemblat, Summe passt):** `swplo` ist ein `daddr_t` (4 Byte) bei `8884`–`8887` = `00 00 00 FA` = **250**, `nswap` ein Wort bei `8888` = `00 F4` = **244**; 250 + 244 = **494** = die ganze 26×128-Diskette.
Belege: `main` (`358C–35A4`) ruft `mfree(swapmap = A0DC, nswap, 1)` und dekrementiert danach `swplo` (V7-Muster: Swapadresse 1 ↦ Block `swplo`), der Blockzugriff `ADDL RR2,%8884` mit `swapdev` steht bei `42F8`, `43C4`, `4470`, `5E72`.
„Out of swap space“ (`8C64`, ausgelöst bei `5692`) und „IO err in swap“ (`8C84`) sind die Fehlertexte.  **Im Lauf nicht ausgelöst** (ein Logpoint auf `5E50` blieb in Anmeldung, `ls`, `sh` still); die Werte sind also *gelesen*, nicht *gemessen*.

1. **Beginn verschieben:** `swplo` (Byte `8887` bei Werten < 256, sonst `8886`/`8887`) und `nswap` (`8888`/`8889`) so setzen, dass `swplo + nswap` ≤ Gerätegröße; `s_fsize` der Wurzel muss ≤ `swplo` bleiben —
   in den Bauangaben der Wurzel `bloecke` (`bauangaben.yaml`, `bau_aus_archiv.py` bricht ab, wenn ein Block ≥ `s_fsize` belegt wäre; `wurzel_pruefen.py` prüft es unabhängig).  Werkzeug: `mutos_patch.py kern --swplo N --nswap M`.
2. **Swap auf ein anderes Laufwerk:** `swapdev` (`887F`) auf den Minor setzen; `swplo` = 0 ist möglich: `main` zieht 1 ab (`35A4`), die erste Swapadresse 1 ergibt dann Block 0 (auf einer reinen Swap-Diskette unkritisch);
   `nswap` = Blockzahl (494 bzw. 608, nicht über die Grenze `0260H` hinaus).
   Die Swap-Diskette muss **dauerhaft** im Laufwerk liegen und im gleichen Verfahren (FM/MFM, Sektorlänge wie `[0003H]`) **formatiert** sein (sonst `44H`/`45H` beim ersten Auslagern); `/dev/swap` nur für `ps` angleichen.  **Nicht ausprobiert.**
3. **Wechselwirkung mit 8×512:** Blockraum 608 statt 494; DISK-ROOT belegt `s_fsize` **352** → `swplo` ≥ 352, also `swplo = 352`, `nswap = 256` (= 352 + 256 = 608); `mutos_patch.py kern --swplo 352 --nswap 256`.  Mit dem heutigen `swplo` 250 würde ein Auslagern das Dateisystem überschreiben (Befund §4.8 am 494er-Abbild).
   `nblocks` des Treibers (`0260`) bleibt, solange die Geometrie 8×512 ist.
4. **Grenzen:** `mem = 196608`; der Kernel selbst belegt rund 36 KB, bleiben ≈ 150 KB für Benutzerprozesse — bei zwei oder drei gleichzeitigen größeren Programmen (`sh` 18 KB, Übersetzerläufe `cc` → `c0` → `c1` → `c2`) wird ausgelagert.
   244 Blöcke = 122 KB Swap reichen nach grober Rechnung für zwei bis drei ausgelagerte Prozessabbilder (**Abschätzung**, nicht gemessen); `out of swap space` bricht den `fork`/`exec` ab, es gibt keinen Hänger.

### 11.6 G) Start mit weiteren Disketten: warum `DISK INITIALIZATION ERROR` / `I/O ERROR`

Zwei getrennte Dinge (beide gemessen):

**(1) Anwesenheitsprüfung** (Zyl. 2, `1046–1078`): wählt jedes der vier Laufwerke (8212, Port 18H), gibt `5FH`/`DFH` an Port 10H und wertet Bit 7 von Port 12H aus; nach der Schleife `[0FCAH] = Konstante AND Anwesenheit`.
Es wird **keine Diskette gelesen**, es kommt nie ein Fehler; Rückseiten (Einheiten 4–7) kommen hier nicht vor.

**(2) Das Lesen der Datenträger macht `ZDOS`** (nicht die Zylinder-2-Initialisierung): `ZDOS` (Ladeadresse 2600H) meldet die Einheiten an.  Gemessen mit einem Logpoint auf `0700` (`IY`, `[IY+11]`, `[IY+12]`) und `bt`:

* **Anmelde-Schleife `2849–2888`** liest für `A = 00H, 20H … E0H` (**Einheiten 0–7**, `ADD A,20H`, Ende bei Übertrag) je 384 Byte von **Zylinder 23** (Auftragsvorlage `2892`).  Fehler `C2` („nicht bereit“) wird toleriert (`28A0: CP C2H` → Puffer freigeben, weiter);
  jeder andere Fehler bricht ab.  Die Einheiten 4–7 beantwortet der Nukleus sofort mit `C2` (`07C8`, D = `C2`, **gemessen** für `80H`…`E0H`; 128/160 sind die Einheiten 4/5).
* **Dateisuche `326B–32B8`** (`DO OS.INIT`, Name ohne Laufwerk, `'*'`): beginnt bei Einheit **1**, geht bis 7 und endet bei **0** (`329A: LD A,01H`; `32AB–32B6`), liest je Einheit die Verzeichnisspur (Zyl. 22, ID 1) und folgt den Zeigern.
  **Einheit 0, auf der `OS.INIT` liegt, kommt zuletzt** — ein Fehler bei B:–D: bricht die Suche ab, bevor die Datei gefunden wird.  `RET NZ` bei `32A2`.
* Eine MUTOS-Diskette in B:–D: liefert zwei verschiedene Fehler: **26×128 (Wurzel, Best-of)**: die Anmelde-Schleife besteht, die Suche liest Zyl. 22 der Einheit 2, deutet Bytes als UDOS-Zeiger (`E1 D2` → Laufwerk 7, Spur 210) und endet mit **`I/O ERROR C2 ON UNIT 00`** (Bildschirm: nur `*`, kein Menü).
  **8×512 (DISK-Satz):** schon die Anmelde-Schleife scheitert an Einheit 1 mit **`C6`** (Zyl. 23, Sektor 1 hat 512 B Datenfeld, der Nukleus erwartet 128) → **`DISK INITIALIZATION ERROR C6`** (die Meldung aus §2).

**Rückseiten (Einheiten 4–7) liest der Start nicht** (der Nukleus antwortet `C2`); eine Wurzel auf der Rückseite von A: wäre von dieser Fehlerquelle nicht betroffen, ist aber aus anderem Grund nicht erreichbar (11.7).

**Minimaler Patch (gemessen, Datei `ZDOS` der Ladediskette, Archiv `dateien/ZDOS`):**

| Offset in `ZDOS` | Adresse | alt | neu | Wirkung |
|--|--|--|--|--|
| 0x27D | `287D` | `C6 20` (`ADD A,20H`) | `37 00` (`SCF`, `NOP`) | Anmelde-Schleife endet nach Einheit 0 (`JR C` springt zum normalen Ende `288A`) |
| 0xC9B | `329B` (Immediate von `329A`) | `01` | `00` | Dateisuche beginnt bei Einheit 0 und endet vor 1 |

`[0FCAH]` bleibt dabei **unberührt** (gemessen: `FF 10` nach dem Start), `mutos_io` sieht also alle vier Laufwerkstypen.  Nur der erste Patch genügt nicht (die Suche läuft weiter), nur der zweite nicht für 8×512 (die Schleife scheitert).
**Ergebnis:** Ladediskette `…k5601` (Archiv-Dateien gepatcht, mit `bau_ladediskette.py` gebaut) mit MUTOS-Wurzel in C: **schon beim Start**: Lader-Menü, `BOOT MUTOS`, `r`, `login: root`, `ls -l /` (mit 8×512-Patch zusätzlich CC1 in B:).
Nebenwirkung: UDOS selbst kennt danach nur noch Laufwerk A:.  `FORM.M` lief mit dem Patch bis zurück zum `*` (Ablauf `1`,`1`,`1`,`Y` je mit Eingabetaste; Ergebnis nicht per Medienprüfung belegt); `FORM.B`, `COPY.*` **nicht geprüft** — sie rufen den Nukleus direkt, sollten also unabhängig sein.
Werkzeug: `mutos_patch.py zdos-einheit0`.  (Keine Alternative über `[0FCAH]`: der Typ 0 für B:–D: würde `mutos_io` die Laufwerke wegnehmen.)

### 11.7 F) Rückseiten als Laufwerke 4–7

* **Nukleus (gemessen/abgeleitet):** zerlegt die Laufwerksnummer in `0777–0785` (`(IY+11) rlca ×3 & 7`) und weist ≥ 4 mit `C2` ab (**gemessen**, 11.6).  Eine **Kopfwahl gibt es im Nukleus nicht**: alle Schreibzugriffe auf Port 10H sind Konstanten
  (`0811 BBH`, `0938 A1H`, `0948 87H`, `0A16 B9H`, `0AD0 ADH`, `0AD9 91H` …); der Controller latcht die Seite aus Bit 2 des Pfadbytes (`81H/83H/85H/87H`, Bit 2 = 0 ↦ Kopf 1, `k5122.cpp` ab Z. 659) — der Nukleus schickt `87H`, also immer Kopf 0.
  `[0FCAH]` (2 Bit × 4 Laufwerke) hat keinen Platz für 8 Einheiten.
* **FORM.\*/COPY.\*:** fragen 0–3 nicht selbst ab (`FORM.M 4029`: `AND 0FH`, dann der Typ aus `[0FCAH]` mit `RRCA`-Schleife — bei Laufwerk *n*+4 **dreht sich der Typ auf Laufwerk *n* zurück**); die Grenze liegt im Nukleus.
* **mutos_io:** `A12A[IX+7]` ohne Maske; Minor 4–7 liest hinter die Tabelle (Byte `A12E` = letzte Maskeneingabe) — **abgeleitet**.  **Kernel:** `rkopen` weist Minor ≥ 4 mit ENXIO ab (11.3), `rrk4`/`rk4`-Knoten gibt es nicht.
* **Folgerung (abgeleitet, nicht versucht):** (a) *Swap auf der Rückseite der Wurzel* (`swapdev = 4,6`) und (b) *eine Diskette mit UDOS vorn und MUTOS-Wurzel hinten* (`rootdev = 4,4`) brauchen **vier** Änderungen zugleich — Nukleus (Einheit ≥ 4 zulassen und Pfadbyte mit Bit 2 = 0 für Lesen **und** Schreiben/Formatieren erzeugen),
  `mutos_io` (Tabelle auf 8), Kernel (`CP #4` bei 0x6AF1, `rootdev/swapdev`), Wurzel (`mknod rk4…`), dazu Meldetext.  Das Boot-ROM bootet nur Seite 0, die Ladediskette bleibt dann in A:, die Wurzel liegt auf der Rückseite derselben Diskette — die Texte `remove … boot - disk` /
  `insert … root` würden entfallen.  Aufwand: mittel bis hoch, **Risiko im Nukleus** (Pfadbyte-Muster `(data & F9H) == 81H` im Controller, Formatschreiber); als Ausweg bleibt die getrennte Swap-Diskette (11.5, Punkt 2).

### 11.9 Offene Punkte

1. 8×512 und 26×128 **zugleich** (Umschaltung nach dem Etikett Zyl. 0 / ID 7 / Offset 75) — nicht entworfen.
2. Geschwindigkeit der 8×512-Fassung (ein Sektor je Auftrag, evtl. eine Umdrehung je Block); Aufträge bis Spurende — nicht versucht.
3. Swap im Lauf **nie ausgelöst** (`swplo`/`nswap`/`swapdev`-Aussagen gelesen, nicht gemessen); ein Last-Test (`cc` mit zwei großen Programmen) und das Verhalten bei `swplo + nswap` > Gerätegröße fehlen.
4. Rückseiten: Nukleus-Kopfwahl nicht gebaut; Auswirkung auf Formatschreiber (`FORM.*`) offen.
5. `FORM.B`/`COPY.*` mit dem ZDOS-Patch (11.6) nicht einzeln geprüft; Auswirkung auf `ACTIVATE`/`CAT` (Einheiten ≥ 1) ungeprüft.
6. Der Kernel-Eintrag `8882` (Wort `0001`) und `888C…` (Tabellenzeiger) nicht gedeutet; `6EE0` vergleicht mit `8882` — Rolle unklar.
7. Alles im Emulator; nichts an echter Hardware.

Wiederholung: `tools/dev.sh tool k1520dbg --em em256 --laufwerke K5601,K5601,K5601 disks/a5120_16_MUTOS/a5120_mutos8000_boot_udos_k5601.hfe -x tools/mutos8000/versuche/<skript>.dbg`
(`wurzel_in_a_maske`, `kernel_root_rk0`; `geometrie_8x512` braucht die gepatchte Ladediskette, Kopfzeile des Skripts).
