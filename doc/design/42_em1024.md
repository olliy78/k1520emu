# Entwurf 42: EM1024 — 1 MB Erweiterungsmodul (Neuentwicklung)

Stand 2026-10-28.  Baut auf `17_a5120_16.md` (EM064/EM256) auf.

> **Die EM1024 ist KEINE historische Karte.**  Es ist kein Robotron-Vorbild bekannt; sie ist eine
> Neuentwicklung auf Wunsch (Experimente mit MUTOS 8000, das ein 64-KB-Segment je Prozess belegt).
> Code, Oberfläche (*Erweiterungsmodul ▸ EM1024 (Neuentwicklung, 1 MB)*) und Doku sagen das ausdrücklich.
> Alle Aussagen unten über Schaltung sind **Entwurf**, nicht gemessen.

## 1. Hardwaremodell (in fünf Zeilen)

1. 1 MB DRAM = 16 Segmente zu 64 KB; Zelle = `SN3..SN0 · 64K + Offset` (U8001) bzw. `SG3P..SG0P · 64K + (A15-8, A14-8, AB13..0)` (U880-Fenster).
2. **U8001, Segmentweiche Modus 2** nimmt SN0..SN3 (EM256: nur SN0/SN1, SN2..SN6 gespiegelt = ignoriert; EM1024: SN4..SN6 sind echt, SN ≥ 16 spiegelt auf `SN & 15`).
3. **Modus 0 und 1 bleiben, wie sie sind:** sie liefern nur zwei Segmentbits (A33 Bit 5/6 bzw. INSTR × N/S) und erreichen deshalb auch am EM1024 nur Segment 0..3.  Begründung: beide Betriebsarten sind Festverdrahtung bzw. ein 2-Bit-Feld des
   A33-Registers; für mehr Bits gäbe es kein Register-Bit, und die EM256-Software (BIOS-Selbsttests, CP/A-Treiber) nutzt Modus 0/1 so.
4. **U880-Fenster:** SG0P/SG1P (PIO B0/B1) bleiben; zwei weitere Bits **SG2P/SG3P** liegen in einem **Zusatzlatch auf `MODADR+8`** (Vorgabe `B0H`; Bit 0 = SG2P, Bit 1 = SG3P; Lesen: `FCH | Latch`).
   PIO B ist voll belegt (B2 /RAMEN, B3 /STOP, B4 RESET16, B5 /TRQ8, B6 PR, B7 /PE) und A22 hat nur 4 Bit je Seite, deren oberes Halbbyte beim Schreiben die Seitennummer (`OUT (C),A`, A auf AB8–15) trägt — beides ist als Ort ungeeignet.
5. **EM064/EM256 bleiben bitgleich:** das Zusatzlatch wird nur bei `EM1024` am Bus angemeldet (Zugriff auf `B0H` geht dort ins Leere), `/RESET` löscht es (Vorgabe 0 = bisheriges Verhalten), der Save-State trägt ein Zusatzbyte nur für EM1024.

## 2. Umsetzung

* `core/cards/em/em.{h,cpp}`: `Variante::EM1024`, DRAM 1 MiB, `cellFor16`: Modus 2 `c.seg & 15` (EM256 `& 3` wie bisher, EM064 modulo 64 KB), `rebuildMap`: Segment `seg_ | segx_<<2`, `kRegSegX = 8`.
  Der U8001 ist wie bei der EM256 segmentiert (Z8001).
* Save-State: Variantenbyte steht schon im Block (Abweisung einer EM256), danach Zusatzbyte `segx_` nur bei EM1024.
* Konfiguration: `A5120Machine::Config::Em::em1024`; Konfigurationstext `em=em1024`; C-ABI `k1520_create_with_em(..., "em1024")`, `k1520_em_variant` → `"em1024"`; Python `K1520Emulator(em="em1024")`;
  `k1520dbg --em em1024` (`dev em` zeigt das Zusatzlatch), `boot_trace --em em1024`; Oberfläche: dritte Wahl im Optionsfeld *Erweiterungsmodul* (`app/profil.py`).

## 3. Auswirkung auf MUTOS 8000 (nur Analyse, nichts geändert)

MUTOS fährt Prozess = ein ganzes 64-KB-Segment ohne MMU (`befund.md`, Speichermodell); Segment 0 ist der Kernel.  Mit 1 MB wären 15 statt 3 Anwendersegmente möglich.  Nötig wäre:

1. **Kernel `startup`** (`tools/mutos8000/kernel/c/machdep.c`, 34F6): die Prüfschleife `for (c = 0x100; c < 0x400; c++)` (Klick = 256 B; `usegm = c & 0x7F00` ist die Segmentnummer in Bits 8–14) müsste auf `c < 0x1000` —
   die Konstante `0x400` im Kernelabzug (eine Befehlskonstante, kein Datenwert).  `usegm` (Maske `7F00`) trägt Segmente bis 127; `maxmem` zählt Klicks (0xF00 = 3840 → `mem = 983040`).
   `if (maxmem > 256) maxmem = 256` begrenzt nur die Prozessgröße (64 KB) und bleibt.
2. **Tabellen im Kernel:** `coremap` (`mfree(coremap, 1, c)` je Klick läuft zu zusammenhängenden Einträgen zusammen; Kartengröße prüfen), Größe von `proc[]`/`text[]`/`nswap` — mehr Anwender im Kern brauchen mehr Prozesse,
   sonst ändert sich nichts Sichtbares.  Handassembler `mch.s` (`copyin/copyout/copyseg/clearseg`, `fuword…`): leiten die Segmentnummer aus Klicknummer bzw. `usegm` ab; im Abzug gegenprüfen, dass nirgends `& 3` steht.
3. **Postfach (`mbx.h`):** `mb_seg` ist ein 16-Bit-`int` (+04), `mb_addr` der Offset; sie tragen also schon Segmente bis 127 — **keine Änderung der Nachrichtenform nötig**.
4. **`mutos_io` (U880-Seite, `mutosio.mac`):** hier liegt der eigentliche Engpass.  `EM_BUS` maskiert das Segment mit `AND 03H` und schreibt `48H+n` an PIO B (`OUT A9H`): für ein Segment ≥ 4 (Auslagern, `physio` in ein Anwendersegment) würde still auf Segment `n & 3` zugegriffen
   — **Datenverfälschung**.  Zu ändern: Maske auf `0FH`, Bits 2–3 zusätzlich an `B0H` (Zusatzlatch) schreiben und `OUT A9H` weiterhin mit `48H + (n & 3)`.  Die Fensterabbildung (`SEITE_ABBILDEN`, A22 an `AFH`) bleibt gleich;
   sie wählt nur Seite und A14/A15 im 64-KB-Segment.  Bei `mb_seg ≥ 16` wäre ein Fehler zu melden (statt Spiegelung).
5. **Warnung zur Umstellung auf 0x1000:** der `startup`-Test (`subyte`/`fubyte` 0x55, danach `clearseg`) erkennt eine zu kleine Karte nur, wenn nichts spiegelt.  Auf der EM256 spiegelt SN4 auf SN0:
   der Test bestuende "erfolgreich" und `clearseg` loeschte das Kernelsegment.  Ein 1-MB-Kernel laeuft also nur auf EM1024; er braucht einen eigenen Abzug (die EM1024 ist keine Voraussetzung des ausgelieferten MUTOS).

## 4. Lauf (2026-10-28)

`k1520dbg --em em1024 --laufwerke K5601,K5601,K5601 …boot_udos_k5601.hfe` mit dem Rezept aus `39_mutos8000.md` §A2: MUTOS bootet unveraendert bis `single user login: root`, Prompt `#`,
**`mem = 196608`** (der Kernel prueft nur bis 0x400 Klicks = 256 KB; die Segmente 4..15 bleiben ungenutzt).  `dev em`: EM1024, Modus 2 (A33=C0), Zusatzlatch 0.
